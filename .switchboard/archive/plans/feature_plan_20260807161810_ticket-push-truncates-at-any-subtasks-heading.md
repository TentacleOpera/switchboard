# Ticket push silently drops everything below a `## Subtasks` heading, even the ticket's own

## Goal

Make ticket push send the operator's full description to the remote, truncating only at the *import-generated* subtasks block and never at a `## Subtasks` heading the ticket legitimately owns. Today any parent ticket whose own description contains a `## Subtasks` section loses that heading and every line after it on every push — silently, with no warning and no way to notice until the remote is inspected.

### Problem

Write a ticket description that organises its own work under a `## Subtasks` heading — an entirely normal thing for a parent ticket — then push it. Everything from that heading to the end of the file is discarded. The push reports success. The remote now holds a truncated description, and the next import can overwrite the local file with that truncated text, making the loss permanent.

### Root cause (confirmed against the code)

> *Line references below were re-verified against HEAD on 2026-08-08. `TaskViewerProvider.ts` has grown ~45 lines since this plan was first written, so every reference in the original draft was stale by that amount; the numbers below are the current ones.*

The push path truncates on the *heading text alone*. The display path was already fixed to require the generated-by-import marker; the push path never got the same treatment.

**The correct, marker-keyed rule already exists** — `src/services/ticketDisplayContent.ts`:

```ts
export function stripImportedSubtasksBlock(content: string): string {
    const idx = content.search(/^##[ \t]+Subtasks[ \t]*\r?\n<!-- generated by import\b/m);
    return idx === -1 ? content : content.slice(0, idx).trimEnd();
}
```

with the file's own header comment stating the invariant explicitly:

> *"Keyed on heading + marker, never the heading alone: a ticket whose own description contains `## Subtasks` must render in full."*

and, two lines later, the assumption this plan disproves:

> *"`rawContent` (edit + push) must keep the block — pushTicketEdits truncates at the heading so it never reaches the remote."*

**But `pushTicketEdits` truncates on the bare heading** — `src/services/TaskViewerProvider.ts:22067-22080`:

```ts
            // The description is only the body up to the first appended section.
            let endIdx = bodyLines.length;
            for (let i = 0; i < bodyLines.length; i++) {
                const trimmed = bodyLines[i].trim();
                if (trimmed === '## Subtasks' || trimmed === '## Comments') {
                    endIdx = i;
                    break;
                }
            }
            const description = bodyLines.slice(0, endIdx).join('\n').trim();
```

`trimmed === '## Subtasks'` matches the operator's own heading exactly as readily as the import-generated one. There is no marker check, and the loop breaks on the **first** match, so a heading appearing early in a long description truncates almost the entire body.

**The generator does emit a distinguishing marker.** `TaskViewerProvider._SUBTASKS_HEADER` (lines 22190-22191):

```ts
    private static readonly _SUBTASKS_HEADER =
        '\n\n## Subtasks\n<!-- generated by import — content below this line is not pushed to the remote ticket -->\n';
```

`_buildSubtasksSection` (line 22255) and the merge path (line 22359) both use `_SUBTASKS_HEADER`, so every block this codebase writes carries the marker. The marker is precisely the signal the push path fails to read.

**A legacy wrinkle exists and must be handled.** `_SUBTASKS_HEADING` (line 22189) is the marker-*less* `'\n\n## Subtasks\n'`, still used as an `indexOf` probe at lines 22404 and 22885 — i.e. files written by older versions carry a `## Subtasks` block with **no** marker. On a published extension with ~4,000 installs, many local ticket files are exactly that. A pure marker-only rule would start pushing those legacy import blocks up to the remote, which is the opposite failure.

**A test currently pins the broken behaviour.** `src/test/tickets-subtask-embedding.test.js:49-54`:

```js
    assert.ok(
        content.includes("trimmed === '## Subtasks'"),
        'pushTicketEdits must retain the trimmed === ## Subtasks truncation guard'
    );
```

That assertion has to move with the fix, not be deleted — it exists so a cleanup pass cannot silently remove the push protection.

## Complexity Audit

### Routine
- The correct predicate is already written, tested in practice, and exported: `stripImportedSubtasksBlock` in `src/services/ticketDisplayContent.ts`. The push path can share the module instead of re-deriving a rule.
- The change is confined to one block inside one method; the surrounding frontmatter-strip / title-extraction / `hostInlineImages` pipeline (`TaskViewerProvider.ts:22046-22117`) is untouched.
- Both providers already share the single `description` local (Linear at 22099, ClickUp at 22113), so one fix covers both.

### Complex / Risky
- **Legacy marker-less blocks are real user data.** Files written before the marker existed have a bare `## Subtasks` block. Switching to a marker-only rule would push those blocks to the remote and pollute the ticket description for the install base. The predicate must be marker-first with a *shape-based* legacy fallback, not marker-only.
- **The shape test must be tight.** An import-generated block is a heading immediately followed by `- [ ] …` / `- [x] …` checklist lines (`_buildSubtaskEntry`, line 22235: `` `- [${done ? 'x' : ' '}] ${title} (${idStr})${statusPart}` ``) plus their optional `  > `-indented description blocks (line 22245). A hand-written parent section is prose, sub-headings, or a mix. Keying the legacy fallback on "heading + a tail that is nothing but that exact shape" is a good discriminator; keying it on the heading alone reintroduces the bug.
- **The `## Comments` clause is not equivalent.** The comment at lines 22067-22071 notes `## Comments` is no longer written to imported docs and the clause is retained defensively for legacy files. It has the same false-positive hazard but a much smaller blast radius. Give it the same treatment, or the same bug ships under a different heading.
- **Silent data loss is the failure mode.** Any residual truncation must be *reported*, not silent — but see the correction below: the existing `warningsAll` channel is labelled "image issue(s)" at the point of composition, so it cannot carry this notice unaltered.
- **Both providers share the truncated `description`.** It feeds Linear's `updateIssueDescription` and ClickUp's `updateTask({ markdown_content })` in the same block, so one fix covers both — and one mistake breaks both.

## Edge-Case & Dependency Audit

### Race Conditions
- None new. `pushTicketEdits` is a read-file → transform → single remote write; the transform added here is pure and synchronous. The existing post-push `registerImportedTicket` touch (22121-22127) is unchanged, so the "synced" recompute keeps its current ordering.

### Security
- No new I/O, no new network calls, no new file writes. The change is strictly *less* destructive than current behaviour: more of the operator's own text reaches the remote and nothing extra is read from disk.

### Side Effects
- **More content is pushed than before.** For a ticket whose description legitimately contains `## Subtasks`, the remote description grows on the next push. This is the fix, and it is additive on the remote — but it is a visible change to remote data, so the manual verification below inspects the remote directly.
- **`hostInlineImages` now sees more body.** It runs on `description` (22092-22107). A larger body means image references that previously sat below the truncation point are now hosted and rewritten. That is correct — they are part of the description the operator wrote — but it means a push can now upload attachments it previously skipped. Expected, not a regression.

### Dependencies & Conflicts
- **Ticket whose own `## Subtasks` is followed by checklist items.** Genuinely ambiguous against a legacy import block. Resolve toward the *marker* when present; when absent, withhold only if the block runs to EOF and every non-blank line in it is a checklist entry or an indented `  > ` description line (the exact shape `_buildSubtaskEntry` emits). Anything else pushes in full.
- **Trailing-whitespace hazard in the legacy shape test.** `_buildSubtaskEntry` renders a blank description line as `  > ` *with a trailing space*. Any editor or lint pass that strips trailing whitespace turns it into `  >`, which a `/^\s{2}> /` test rejects — the block then reads as human-authored and gets pushed to the remote, the exact failure this plan exists to prevent. The predicate must accept `  >` at end-of-line.
- **Heading variants.** `stripImportedSubtasksBlock` matches `^##[ \t]+Subtasks[ \t]*` — it tolerates extra spaces but not `###` or trailing punctuation. Reuse the same anchor so display and push agree character-for-character; two subtly different regexes on the same file is how this class of bug returns.
- **Multiple candidate headings in one legacy file.** A pre-marker file can hold a human `## Comments` prose section *above* a generated `## Subtasks` checklist. A first-match-wins legacy probe lands on `## Comments`, finds prose in its tail, declares "nothing generated here", and pushes the checklist block. The predicate must consider *every* candidate heading and take the earliest one whose tail-to-EOF is generated-shaped.
- **Fenced code blocks.** A `## Subtasks` line inside a ``` fence would be matched by a line-anchored regex. `KanbanProvider.ts:12134` already documents this exact hazard for the feature-plan analogue. Low frequency for tickets; note it, do not over-engineer — the marker requirement already removes the common case.
- **CRLF.** `pushTicketEdits` splits on `/\r?\n/` and re-joins with `\n` (22049, 22065), so the helper never sees a `\r` on this call path. It keeps `\r?` in its own patterns anyway, because it is exported and the display-side sibling is called on raw file content.
- **`## Comments` in a real description.** Same treatment: require it to look like an appended block (runs to EOF, generated shape) rather than truncating on the heading.
- **Round trip:** after this change a parent ticket with its own `## Subtasks` pushes in full; the next import overwrites the local file from the remote and the section survives. Verify this end-to-end, because the previous behaviour meant the section was destroyed on the *second* import, not the first.
- **Migrations:** no schema or file-format change. The only behavioural change on existing files is that more content is pushed — additive on the remote, never destructive locally.
- **Files touched:** `src/services/ticketDisplayContent.ts` (add one exported helper), `src/services/TaskViewerProvider.ts` (`pushTicketEdits` only), `src/test/tickets-subtask-embedding.test.js` (retarget the pinning assertion, add helper unit cases).

## Adversarial Synthesis

**Risk Summary.** The dominant risk is not the marker path — it is the legacy fallback, which decides on *shape* whether ~4,000 installs' pre-marker `## Subtasks` blocks reach the remote. Too loose and legacy import blocks pollute remote descriptions; too tight (trailing-whitespace sensitivity, first-match-wins heading scan) and generated blocks leak on exactly the files the fallback exists to protect. Mitigations: a whitespace-tolerant `  >` test, an all-candidates heading scan that picks the earliest generated-shaped tail, unit coverage for all five shape cases, and a user-visible notice when a block is withheld so a wrong verdict is observable rather than silent.

## Proposed Changes

### `src/services/ticketDisplayContent.ts` — one shared truncation rule for both display and push

Add a push-side sibling next to `stripImportedSubtasksBlock`, so the two paths cannot drift:

```ts
const APPENDED_HEADING = /^##[ \t]+(?:Subtasks|Comments)[ \t]*\r?$/gm;

/**
 * Cut the appended, import-generated tail from a ticket body before pushing it to the
 * remote — and ONLY that tail.
 *
 * Marker-first: a block carrying `<!-- generated by import` is unambiguous and is always
 * cut (this is what _SUBTASKS_HEADER writes today). Legacy fallback: files written before
 * the marker existed carry a bare `## Subtasks` block, so a heading whose tail runs to EOF
 * and contains nothing but `- [ ]` / `- [x]` checklist lines and their indented `  >`
 * description blocks is treated as generated too — that is exactly the shape
 * _buildSubtaskEntry emits and nothing a human writes by hand.
 *
 * Everything else stays. A parent ticket whose own description has a `## Subtasks`
 * heading — prose, sub-headings, anything not that exact shape — pushes in full.
 * Returns the body to push plus a flag so the caller can warn instead of losing content
 * silently.
 */
export function stripAppendedBlocksForPush(body: string): { pushBody: string; withheld: boolean } {
    const markerIdx = body.search(/^##[ \t]+(?:Subtasks|Comments)[ \t]*\r?\n<!-- generated by import\b/m);
    if (markerIdx !== -1) {
        return { pushBody: body.slice(0, markerIdx).trimEnd(), withheld: true };
    }

    // Legacy (pre-marker) files. Scan EVERY candidate heading, not just the first: a
    // legacy file can carry a human `## Comments` prose section ABOVE the generated
    // `## Subtasks` checklist, and a first-match-wins probe would land on the prose,
    // conclude "nothing generated here", and push the checklist to the remote.
    APPENDED_HEADING.lastIndex = 0;
    for (let m = APPENDED_HEADING.exec(body); m; m = APPENDED_HEADING.exec(body)) {
        const tail = body.slice(m.index).split(/\r?\n/).slice(1);
        const meaningful = tail.filter(l => l.trim() !== '');
        // `  >` NOT `  > ` — _buildSubtaskEntry renders a blank description line as
        // `  > ` with a trailing space, and any trailing-whitespace strip (editor,
        // formatter, git filter) turns it into `  >`. Requiring the space made a
        // whitespace-normalised legacy file look human-authored and pushed its
        // generated block to the remote.
        const looksGenerated = meaningful.length > 0
            && meaningful.every(l => /^- \[[ xX]\]/.test(l.trim()) || /^[ \t]{2,}>(?:[ \t].*)?$/.test(l));
        if (looksGenerated) {
            return { pushBody: body.slice(0, m.index).trimEnd(), withheld: true };
        }
    }
    return { pushBody: body, withheld: false };
}
```
