# Browser Memo Panel

**Complexity:** 6

## Goal

Bring the browser cockpit's Memo panel up to standard: restyle it onto the shared panel token set (removing the default-theme neon repaint), make Copy Prompt / Send to Planner actually clear the panel and confirm the clipboard write, and stop it binding to the wrong workspace and emitting cross-workspace project pins.

The Memo panel is the one browser panel that was written as a standalone page rather than assembled from the shared panel vocabulary, and all three defects trace to that: its own miniature palette (which repaints the *default* theme neon), its own untyped return path (so the host clears `memo.md` while the browser never learns), and a workspace root baked in at server-start time (so it wrote one repo's memo while the board showed another). The three subtasks are grouped because they are the same panel, the same two webview files, and — for two of them — the same `memoGeneratePrompt` arm; shipping them independently would mean three collisions on `memo.html`, `memo.js`, and `TaskViewerProvider.ts`.

## How the Subtasks Achieve This

- **Restyle the Browser Memo Panel to Switchboard's Panel Design Language**: rebuilds `src/webview/memo.html` on the canonical token set from `setup.html` and the canonical `.secondary-btn` / `.section-label` / `.modal-textarea` classes from `implementation.html`, adds real panel chrome, and drops every inline `style`. Critically it inverts `body.cyber-theme-enabled` from a full neon repaint to a non-repainting class — that selector is what `getThemeBodyClass()` returns for afterburner, the **default** theme, so the panel most users see was the one that looked least like Switchboard. It lands first because it also defines the tokens (`--accent-green`, `--accent-red`) and reserves the markup hooks (`.is-copied`, `#memo-workspace`) the other two subtasks need.
- **Browser Memo Panel: Clear the Memo on Copy/Send and Confirm the Clipboard Copy**: fixes the *notification* back to the browser — the clipboard itself already works, because the extension host writes the system clipboard through its own seam. The response body gains a `type` so `transport.js` can route it and a `memoCleared` flag so `memo.js` knows to empty the textarea; the panel then shows the count-and-cleared status and flashes the button that was pressed. It also persists the API server on `TaskViewerProvider` so its `BroadcastHub` is no longer built with `apiServer: null` (today **no** TaskViewer push reaches any WS/browser client) — sibling-provider parity, sidebar↔browser sync, and the prerequisite for subtask 3.
- **Browser Memo Panel Writes to the Wrong Workspace: Unfreeze Its Workspace Root and Stop Cross-Workspace Project Pins**: replaces the workspace root captured once in `_startLocalApiServer`'s closure with a per-render getter, so every panel (not just Memo) binds to the workspace the board is actually showing; teaches `memo.js` to display that workspace and to follow a host-side switch without letting a pending debounced save write the old workspace's text to the new root; and adds a destination-workspace guard so a resolved project name is only emitted as a `PROJECT PIN` when it actually exists in the workspace the prompt targets — plus scoping `KanbanProvider`'s cross-workspace `_projectFilter` singleton, which is what leaked one board's project into another board's prompt.

## Dependencies & sequencing

**Cross-feature dependencies:** none. Every file this feature touches is already in the working tree, and no other feature's output is required.

**Shipping order — strict, not advisory.** All three subtasks edit `src/webview/memo.html` and/or `src/webview/memo.js`, and subtasks 2 and 3 both edit the *same* `memoGeneratePrompt` arm in `src/services/TaskViewerProvider.ts`. Per the Browser Switchboard PRD's orchestration discipline (one agent stream per provider file), they serialise:

1. **Restyle** — first. It rewrites `memo.html` wholesale, so any earlier edit to that file is a guaranteed conflict. It also owns the two tokens and the two markup hooks the others consume.
2. **Clear on Copy/Send** — second. It needs Restyle's `memo.html`, and it must precede subtask 3 twice over (see below).
3. **Frozen workspace root** — last. Hard-blocked, not merely ordered.

**Prerequisites and guards:**

- Subtask 3's live workspace-follow is **dead code without subtask 2**. `workspaceChanged` reaches a browser client only through `TaskViewerProvider.postMessage` → `BroadcastHub.mirrorToWs`, which is a no-op while the hub's `apiServer` is unset — exactly the condition subtask 2 fixes. Shipped alone, subtask 3 degrades to "correct root on panel open". This is the only dependency subtask 3 has on subtask 2.
- Subtask 1 reserves the empty `#memo-workspace` span in `.memo-header` (moved out of subtask 3) and the `--accent-green` / `--accent-red` tokens that subtask 2's `.is-copied` and error-status colours read (moved out of subtask 2's literal-hex fallbacks). No subtask re-opens another's file. Subtask 3 owns the `WS_ROOT` → `_wsRoot` conversion in `memo.js` uncontested — subtask 2 adds no `workspaceRoot` payload site.
- **No browser-side clipboard write in the extension host.** Subtask 2 deliberately does not echo `prompt` back to the browser: the host already wrote the system clipboard, a second write would be redundant, and WebKit rejects a clipboard write issued after a `fetch()` boundary (`NotAllowedError` — it requires the call to sit on the user-gesture call stack, unlike Chromium/Gecko which keep transient activation alive ~5s across promise ticks). The standalone `npx` host has no VS Code clipboard so it must keep returning `prompt`; that path inherits the WebKit limitation and is documented as pre-existing and out of scope. Consequence for testing: subtask 3 reads the generated prompt from the clipboard **seam recorder**, not from a response field.
- After any subtask that edits `TaskViewerProvider.ts`, `npm run catalog:check` will report drift because `protocol-catalog.json` records push sites by line number — regenerate and commit it in the same change.
- `getMemoHtml` prefers `dist/webview/memo.html` over `src/`, and the installed extension serves from its own install folder: rebuild **and** sync **and** reload before judging any of the three, or a stale `dist` looks identical to "the change did nothing".
