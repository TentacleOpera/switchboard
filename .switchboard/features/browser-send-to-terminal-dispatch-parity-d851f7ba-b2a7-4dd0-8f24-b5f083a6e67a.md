# Browser Send-to-Terminal Dispatch Parity

**Complexity:** 8

## Goal

Every browser-originated prompt dispatch reaches the terminal the calling surface can display, and reports honestly when it cannot. The browser rail already stamps apiOriginated on every request (LocalApiServer._stampHttpSurface), but only 2 of 8 _dispatchExecuteMessage call sites pass the resulting allowPtyFleet flag, four helpers bypass the dispatcher entirely and drive vscode.Terminal directly (two of them creating an invisible terminal on miss), several report success on a failed delivery, and the clipboard fallbacks write the extension host's clipboard rather than the browser's. Subtasks: (1) dispatchCustomPromptToRole + its 8 call sites; (2) the four stray _dispatchExecuteMessage sites — orchestrator kickoff/wake, pair-programming coder, Airlock send-to-coder; (3) the four direct-to-vscode.Terminal helpers and the arms that hardcode success; (4) project-panel verbs rejected by the Planning allowlist (improvePlan, webviewReady).

> **Superseded:** "The browser rail already stamps apiOriginated on every request (LocalApiServer._stampHttpSurface) … only 2 of 8 _dispatchExecuteMessage call sites pass the resulting allowPtyFleet flag."
> **Reason:** Both counts were checked against source on 2026-08-06 and both are wrong in ways that change the work. (a) `_stampHttpSurface` is called from only **four of seven** verb-rail handlers — `_handleDesignVerb` (`LocalApiServer.ts:1865`) and `_handleSetupVerb` (`:1901`) never stamp, so `apiOriginated` is permanently `undefined` on `/design/verb/*`. That makes the design-panel half of subtask 3 a no-op unless the stamp is added, which is why subtask 3 now owns that fix as a blocking prerequisite. (b) `_dispatchExecuteMessage` has **seven** call sites, not eight: two pass the flag (`:5411`, `:19316`), five do not (`:4675` in subtask 1; `:9387`, `:9975`, `:10923`, `:21411` in subtask 2). Subtask 2's contract test asserts on that count, so the wrong number would have failed on correct code.
> **Replaced with:** the stamp covers the kanban, planning (which also serves `/project` and `/memo`), tickets and taskViewer rails only; the design and setup rails are gaps this feature closes. `_dispatchExecuteMessage` has seven call sites, two of which already pass `allowPtyFleet`.

## How the Subtasks Achieve This

- **Browser "Send to Planner" Fails Because the Dispatch Path Drops the Surface Flag** (complexity 6): threads `apiOriginated` into `TaskViewerProvider.dispatchCustomPromptToRole` as a trailing, fail-closed `options` parameter and forwards it to all three of its consumers (planner-set resolution, `_resolveAgentTerminalForPlan`, `_dispatchExecuteMessage`), then updates all eight call sites across `PlanningPanelProvider` (×5), `KanbanProvider`, the memo arm and the tickets `askAgentTask` command boundary. It also makes the failure honest in the browser by returning `error` + `prompt` in the reply body — the only way a cockpit user gets the promised clipboard fallback. This is the highest-traffic single method in the feature: seven user-facing buttons funnel through it.
- **Four Dispatch Sites Hardcode the VS Code Fleet, So Orchestrator / Pair-Program / Airlock Sends Die in the Browser** (complexity 6): fixes the remaining four bare `_dispatchExecuteMessage` sites. Orchestrator kickoff and wake get the surface *remembered on run state* (`_orchestratorApiOriginated`) because the wake fires from a timer with no request in scope, set at both start entry points (the `startOrchestrator` verb arm and the LocalApiServer `orchestrationStart` callback). Pair programming gets the flag through `dispatchToCoderTerminal` **and** through `KanbanProvider._dispatchWithPairProgrammingIfNeeded`'s ten call sites — the board's actual pair path. Airlock gets both the flag and the `workspaceRoot` its resolution was missing, plus a real failure report instead of an unconditional "sent".
- **Four Direct-to-`vscode.Terminal` Helpers Bypass the Dispatcher, So Browser Sends Land in Invisible Terminals and Still Report Success** (complexity 8): the largest subtask and the only one that changes behaviour rather than just routing. It adds one shared fleet-first pre-step (`_tryFleetDeliveryForRole`, an authoritative `ptyListTerminals` role match delivering through `_dispatchExecuteMessage`), makes the four bypass helpers use it, and stops them conjuring a VS Code terminal for a browser caller — failing with the prompt in the body instead. It also converts three `void` return types to `boolean` so the eleven call sites can stop hardcoding `{success:true}`, closes the `_handleDesignVerb` / `_handleSetupVerb` stamp gap that the rest of its own fix depends on, and lowers the `"Planning"` return-contract ratchet ceiling to lock the `break` → `return` conversion in.
- **Project Panel Posts Two Verbs the Planning Allowlist Rejects, So the Browser Shows an Error Banner on Every Open** (complexity 4): the one non-dispatch subtask. It catalogues `webviewReady` so the project panel stops 500-ing on every open, and delegates `improvePlan` to `KanbanProvider.handleServiceVerb` *before* the `PLANNING_VERBS` guard so the verb reaches its real implementation with that provider's own schema validation — repairing the Improve button in both hosts. Without it, the browser project panel greets the user with a red banner regardless of how well the dispatch paths work, which is why it belongs in this feature rather than a UI one.

## Dependencies & sequencing

**Cross-feature dependencies:** none. Every mechanism this feature threads (`allowPtyFleet` on `_dispatchExecuteMessage` / `_attemptDirectTerminalPush` / `_resolveAgentTerminalForPlan` / `_getAgentNameForRole`, the `_stampHttpSurface` discriminator, the `transport.js` failure-body clipboard convention) is already shipped and exercised by the board's own api-originated dispatch path. Nothing from another feature must land first.

**Shipping order within the feature — the subtasks are independent and may land in any order.** The reconciliation audit found no contradiction and no supersession between them; each owns a disjoint method set. Two coupling points exist and neither imposes an order:

1. `PlanningPanelProvider.ts:4226/4342/4355/4374/4410` — subtask 1 edits the `dispatchCustomPromptToRole(...)` call; subtask 3 edits the `_sendPromptToTerminal(...)` fallback on the *next* line of the same five arms and converts their `break`s to typed returns. Whichever lands second adds one argument to an already-edited block. No logical conflict.
2. `_dispatchExecuteMessage` call-site count — subtask 3 **adds** an eighth site (inside `_tryFleetDeliveryForRole`), while subtask 2's contract test asserts over those sites. Resolved by construction: subtask 2's test asserts the *property* (every site passes an explicit sixth argument) plus a `>= 7` floor, never an equality. If subtask 2 lands first with an equality count, fix the assertion rather than weakening it.

**Ordering that IS required, and it is internal to subtask 3:** its Proposed Changes §0 (stamp `_handleDesignVerb` / `_handleSetupVerb`) must land with or before its §4 (the four `DesignPanelProvider` arms). §4 without §0 is a verified no-op that passes every source-level test.

**Prerequisites and guards:**

- **Fail-closed default is the non-negotiable invariant across all four subtasks.** Every new surface parameter is trailing, optional, and derived as `!!options?.apiOriginated`. The single sanctioned exception is the LocalApiServer `orchestrationStart` callback (`TaskViewerProvider.ts:2390`), which passes a literal `true` because it is an HTTP-only path with no body to read; subtask 2's contract test allowlists it by name with that reason.
- **Owner of the ratchet baseline is subtask 3 alone.** It is the only subtask that converts `break` to `return` in a provider `_handleMessage`, so it is the only one that may touch `scripts/verb-return-contract-baseline.json` (`"Planning": 165` → the true post-conversion residual from `analyze-verb-migration2.js`). The other three must show a clean `npm run verb-returns:check` with no baseline edit; a ratchet diff in subtasks 1, 2 or 4 means scope leaked.
- **One agent stream per provider file** (project PRD orchestration discipline). Subtasks 1, 2 and 3 all edit `TaskViewerProvider.ts`, and subtasks 1, 3 and 4 all edit `PlanningPanelProvider.ts` — so they must be coded **serially**, not fanned out in parallel worktrees, even though they can be merged in any order.
- **A PTY-less install must stay byte-identical.** Every fleet branch guards on `this._ptyHostPort`, so all four subtasks degrade to today's VS Code-only behaviour when the fleet is not running. Each subtask carries a fleet-less regression step; do not sign off without it.
- **Verification is browser-side or it is nothing.** The failure reports these paths produce today are `showErrorMessage` / `showWarningMessage` VS Code toasts, invisible in a browser tab. Every "the fix works" claim must be evidenced by reading the browser terminal or pasting from the *browser* clipboard — never by a green contract test, which in this feature can pass while the flag is `undefined` at the boundary.
