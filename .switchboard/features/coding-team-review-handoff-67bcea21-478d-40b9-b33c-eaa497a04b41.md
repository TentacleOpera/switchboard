# Coding team review handoff

**Complexity:** 8

## Goal

Close the loop between a coding team's lead and its reviewer. Today the shipped Coding team ships a reviewer as its last member but nothing ever hands work to it: wireSpawnedTeam's team-scoped standing order deliberately excludes the head, so there is no channel for head-directed instructions, and a finished subtask sits in CODER CODED until a human drags it. Separately, once work IS advanced to CODE REVIEWED, role resolution is workspace-wide and team-blind — getRoleTerminalSet and _resolveAgentTerminalForPlan pick the first alive reviewer by alphabetical sort or fleet order, so a card coded by one team routinely lands on another team's reviewer while its own sits idle. Team membership is already recorded in terminals.groups (including the unparented scope:'shared' reviewer); the dispatch path simply never reads it. Subtask 1 adds a team-head standing-order scope and a headPrompt telling the lead to advance finished subtasks via POST /kanban/dispatch. Subtask 2 makes that advance resolve the reviewer on the originating team. Neither blocks the other.

## How the Subtasks Achieve This

- **Coding team: give the head a standing order to advance finished subtasks to CODE REVIEWED**: Builds the missing *channel*. Adds a fourth standing-order scope, `team-head`, to `standingOrders.ts` and its hand-written client mirror in `terminals.js` — the exact complement of the existing `team` scope, which deliberately excludes the head and therefore left no way to instruct one. `wireSpawnedTeam` installs one `team-head` order per team when the team definition carries a `headPrompt`, and the shipped `Coding` team gains that field: a standing instruction to `POST /kanban/dispatch` with `targetColumn: "CODE REVIEWED"` and `"from":"{head}"` (interpolated to the head's own terminal name at install time), plus an explicit warning not to use `/kanban/move`, which moves a card and dispatches nobody. It also repairs a silent data-loss path found during planning: the TEAMS editor reconstructs a team from form fields on save and destroys any key it does not read, so a Head-prompt field is mandatory or the first Save after adopting the team wipes the instruction.
- **Route a CODE REVIEWED advance to the originating team's own reviewer, not the first reviewer on the board**: Makes the *destination* correct. Adds a pure `resolveTeamScopedRoleTerminal` helper that reads the `terminals.groups` roster — the authoritative membership record `wireSpawnedTeam` already writes, including the unparented `scope:'shared'` reviewer — and returns the live terminal of the requested role on the origin's own team, or `null` rather than a guess. `POST /kanban/dispatch` accepts `from`, resolves the override, and echoes a `teamRouting` line naming the decision (including every fallback). It also fixes the two things that would have made this a half-fix: the `custom-user` dispatch branch silently discarded caller overrides, and `plans.dispatched_agent` — the origin signal for the human drag path — was being recorded as the literal string `'unknown'`, so the drag path had no origin to resolve at all.

## Dependencies & sequencing

- **Functionally independent — either subtask is useful and shippable alone.** Subtask 1 closes the loop on a single-team board (there is only one reviewer to reach). Subtask 2 corrects routing for human drags and for orchestrator/oversight dispatches, none of which involve a team head. Neither is a precondition for the other's correctness.
- **They must nevertheless serialise on one file: `src/services/teamWiring.ts`.** Subtask 1 extends `WireSpawnedTeamOptions` and adds a push inside the standing-orders mutator; subtask 2 appends the `resolveTeamScopedRoleTerminal` helper. Different regions, same file — the project's orchestration rule is one agent stream per provider file. **Land subtask 1 first**: it is the smaller edit to that file, and it is the one whose scope-widening (`StandingOrderScope`) is compile-checked, so a conflict surfaces as a build error rather than a silent merge.
- **The `from` contract is owned by subtask 1, consumed by subtask 2.** Subtask 1's `headPrompt` ships `"from":"{head}"` in its documented POST body from the start. `_handleKanbanDispatch` reads a fixed set of body keys and ignores unknown ones, so the field is inert until subtask 2 lands and correct the moment it does. Subtask 2 therefore does **not** edit `kanban.html` — it only documents `from` in the orchestration skill. Do not re-introduce a conditional "update the headPrompt if the other change is present" step; that ordering dependency was removed deliberately.
- **Guards that must already hold:** the `Coding` team must have been adopted (TEAMS tab → USE) and started, since both subtasks read state that only a team start writes — `terminals.standingOrders` for the head order, `terminals.groups` for the roster. On a board with no registered groups, subtask 2 resolves to `null` and behaves exactly as today.
- **Verify in this order after both land:** subtask 1's editor round-trip (adopt → Save → re-open → head prompt still present) before anything else, because a wiped `headPrompt` makes every downstream test pass for the wrong reason.
