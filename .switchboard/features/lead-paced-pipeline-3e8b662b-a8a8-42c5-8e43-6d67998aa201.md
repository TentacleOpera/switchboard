# Lead-Paced Pipeline

**Complexity:** 7

## Goal

Replace the three automation modes with a queue the coding lead walks itself, and rescope the orchestrator from resident manager to advisor that hands off and exits.

The pacing clock exists to answer one question — "is it time to dispatch the next card?" — that the lead can now answer directly. Four of the five steps in a feature's life are already agent-driven pushes: a coder reports to its head, the head hands out the next subtask, the head dispatches the finished feature to review with one `POST /kanban/dispatch`, and the reviewer reports back. Only step five, "get the next feature", has no instruction — and `scheduled`, `agent-managed` and `external` all exist to fill that single gap. Closing it with a message instead of a clock removes three subsystems and their interlocks.

The second half is scope. For a one-at-a-time pipeline a resident orchestrator is a manager watching a manager: it wakes on a timer to observe a fact the lead was already told by its own reviewer. The orchestrator's real value is judgement — verifying teams are set up, deciding what is in scope, decomposing work, advising a user who does not know where to start, and coordinating multiple teams across worktrees or repos. That work is advisory and episodic, so the session should end when it is done.

## How the Subtasks Achieve This

- **The Coding Lead Paces Its Own Pipeline — `POST /kanban/queue/next`**: Adds the pull entry point to the run sheet's own `PLAN REVIEWED → coder head` step: a serialized pop that dispatches through the existing `performKanbanDispatch`, refuses a team that already has work in flight, and returns `dispatched: null` on an empty queue. One sentence on the coding head prompt — carried as a `team-head` standing order, so it survives a `/clear` — tells the lead to make the call when review passes. This is the missing link; nothing is deleted here.
- **The Dispatch Column Becomes the Session Queue**: Turns the existing `DISPATCH` staging column into an ordered queue. It already has multi-select, a staged-card count and a fan-out button; what it lacks is order and a paced entry point. Adds `queue_position`, drag-to-reorder inside the Dispatch view, staging from a selection, and a `Run queue` button that dispatches card one through the same endpoint the lead uses — so cold start and steady state share one code path. Parallel fan-out (`Send all to coders`) is kept for the multi-coder case.
- **A Dead Pacer Must Surface, Not End the Night Silently**: Adds a queue watch to the existing `_runFeatureNudgeSweep`, whose four gates (head live, head not mid-turn, nothing in flight, no turn-end this tick) and evidence-composing nudge are already exactly what a stalled pacer needs. Wakes the lead once with the state, escalates to the user on the second nudge, and notifies rather than silently dropping the watch when the head is gone. This is the backstop that makes deleting the clock safe, which is why it is a prerequisite rather than a follow-up.
- **Delete the Mode Axis and the Completion Hybrid**: Removes the coupling, **keeps scheduling**. The UAT failures come from four things, none of which is a clock: `completion` as a trigger mode *inside* the run-sheet engine (which forces `_autobanLaneInFlight`, since one turn-end walks every step), mutual suppression between that hybrid and the cron, three exclusive modes each having to disable the others' timers, and completion inferred from plan-file `mtime`. A plain scheduler needs none of that — it needs no agent, cannot misjudge, and survives a dead lead. So the schedule becomes a third caller of `queue/next` beside the lead and the `Run queue` button, and that endpoint's `409` in-flight refusal replaces every suppression guard: one serialization point arbitrates, so a schedule and a self-pacing lead can both be live. Deletes the trigger modes, the completion hybrid, the run sheet as a decision structure and the mode axis; keeps the interval, the cron, the per-dispatch stall watchdog, turn-end detection, and both survivor jobs.
- **The Orchestrator Becomes an Advisor**: Fixes the reported essay problem at its three roots — the pre-flight reports passing checks as findings, "ready to go" is never defined as a query, and the injected project filter is never explained. Makes passing checks silent, adds one deterministic `## The ready set` definition (HTTP not the markdown exports, which cannot express subtask exclusion; explicit column and subtask exclusions; a stated answer ceiling), points the two existing consumers at that one definition, and documents the two advisory entries the persona omits.
- **The Orchestrator Hands Off and Exits**: Adds the terminal state the session model is missing. Today there are only two states — interviewing and armed — and `/orchestration/confirm` is the only exit from the pre-flight, so an orchestrator with nothing left to do arms and idles by construction. Adds `POST /orchestration/handoff`: scope, launch the team, stage the queue, dispatch card one, report, exit. Arming becomes multi-team-only and must be justified in one line.
- **Remote Plans Enter the Queue, Not the Agents**: Stops a batch of remote status changes from becoming a batch of simultaneous agent runs. The poll loop dispatches per delta and `onColumnMove` returns when the prompt is *sent*, so five Notion issues moved at once start five concurrent agents, uncapped — and the only existing defence is binary (`ingest` disables remote execution entirely; `full` fires everything). Adds a third `queue` mode that stages arrivals into the session queue in arrival order and lets the lead walk them one at a time. **Stays fully extension-managed and requires no orchestrator** — staging is mechanical, so no judgement sits in the correctness path of the one mechanism whose value is having none. Optional batch sequencing (reorder by dependency, group what belongs together) is an explicit setting, default off, bounded so an absent sequencer falls back to arrival order rather than holding the queue shut.

## Dependencies & sequencing

- **Ordering constraint — it attaches to subtask 1, not subtask 4.** Since scheduling survives (subtask 4 keeps it), the old "the clock is the only thing that restarts a stalled lane" argument no longer binds 3 before 4. What binds is that **subtask 1 is what introduces unpaced pull**: a session with the schedule off has no clock to recover a stalled lead, so subtask 3's queue watch must land alongside 1 before pure-pull pacing is offered to users. Subtask 4's only hard prerequisite is 1, because the schedule calls `queue/next`.
- **Scheduling is also a recovery path.** With a schedule enabled, a stalled lead is picked up by the next tick — which makes subtask 3 the backstop for the schedule-off case specifically, rather than for the feature as a whole. Worth remembering when deciding how hard to push on 3's escalation behaviour.
- **Subtask 6 depends on 1 and 2** — handoff dispatches card one through `queue/next` into a staged queue.
- **Subtask 7 depends on 1, 2 and 3** — it needs a queue to stage into, a lead that pulls from it, and the queue watch its staging arms. The dependency on 3 was missed in an earlier draft and is not cosmetic: subtask 7's success case is *five cards staged and nothing started*, which is indistinguishable from an outage unless the watch is armed at staging. Its bug fix is still entirely extension-managed and involves no agent, so it does **not** depend on 6; only its opt-in sequencing layer wants 6's handoff endpoint and writes the persona, and that layer can ship later or never without weakening the fix. It adds no session state.
- **Scope note for subtask 4 — read this before coding it.** It deletes *coupling*, not timers. Scheduling is kept as a first-class option; so are the `RemoteControlService` provider poll (inbound transport) and the survivor jobs `fetch-plans` and `reconcile`, which today have no interval of their own and hang off the run-sheet tick (`TaskViewerProvider.ts:12367`). Because the tick is being restructured, they must be explicitly re-attached and tested as subtask 4's **first** commit — deleting the tick under them fails with **no compile error and no failing test**, so cloud-VM plans silently stop arriving and completion reports silently stop advancing cards.
- **The scheduler surface itself is already retired** and is not in this feature's scope: custom jobs are dropped on read with a one-time notice, records preserved in `integration-config.json`. Notably, the two presets were *kept* when it went — evidence that scheduled work is useful independently of the surface that drove it, which is why subtask 4 keeps scheduling rather than deleting it.
- **Pull and schedule are not competitors.** "Start at 2am" and "start the next card when the last one finishes" are different questions. Subtask 1's server-side `409` in-flight refusal is what lets both be live at once with no mutual-suppression logic — it is the single serialization point the whole feature rests on, which is why subtask 4 depends on it rather than the reverse.
- **Subtask 5 is independent and should ship first.** It is the one that addresses the reported failure directly, needs nothing from the others, and shrinks the persona that subtasks 4 and 6 both go on to edit — so landing it early avoids three passes over the same file.
- **Suggested order**: 5, then 1 and 2 (parallel-safe, different layers), then 3 (pairs with 1 — it covers the schedule-off case 1 introduces), then 7's steps 1–4 (its fix needs 1, 2 and 3, and touches no persona), then 6, then 4 last as the decoupling pass. 7's sequencing layer, if wanted at all, lands after 6 — it is the only part of 7 that writes the persona, which is why 7 can precede 6 without breaking the persona serialisation.

- **Prerequisites/guards**: no migration of the *automation* state is required (the operator has confirmed the shipped automation is not worth preserving), but two guards are non-negotiable. The legacy-state guard in subtask 4 inverts the existing `normalizeAutomationMode` default, which currently maps unrecognised values onto a *running* mode specifically so an upgrade cannot disarm a board. And subtask 2 adds a column to the shipped `plans` table, so it needs `SCHEMA_TABLES_SQL` **and** a gated `MIGRATION_V60_SQL`, with no edit to any shipped V51–V59 body.
- **Persona edits serialise.** Subtasks 5, 6, 7 and 4 all write `.agents/skills/switchboard-orchestrator/SKILL.md`, and 5, 6 and 7 all write the persona gate `src/test/orchestrator-tick-and-reports-contract.test.js`. One agent stream per file: 5 → 6 → 7 → 4. Same-file parallel edits collide.

## Reconciled end-state

The cross-subtask audit found four contended surfaces. Each has one owner and one design; a coder implementing any subtask should treat this as the arbiter.

| Surface | Owner | Reconciled decision |
| :--- | :--- | :--- |
| The queue pop | Subtask 1 | `dispatchNextFromQueue()` is the contract; `POST /kanban/queue/next` is a thin wrapper. Subtasks 2, 4 and 6 call the **method in-process** — no localhost round-trips against our own server. This is what makes "one serialization point" and subtask 3's "one arming site" true rather than aspirational. |
| In-flight refusal | Subtask 1 | A team is in flight when it holds a card in a **coding column** (`LEAD/CODER/INTERN CODED`) — not when a card carries `dispatched_at`. The original predicate refused the head's own legitimate call (its just-reviewed card still carries `dispatched_at`, naming the reviewer) and would have stopped every pipeline after card one. |
| The queue watch's arming trigger | Subtask 3 | Arm on **staging or dispatch**, whichever comes first, via one shared `armQueueWatch`. Dispatch-only arming left subtask 7's remote batches and any pre-team staging unwatched — the exact silent night the watch exists to prevent. |
| The armed orchestrator state | Subtasks 4 + 6 | The **exclusive three-mode axis** dies; the orchestrator wake does not. `AutobanAutomationMode` goes, replaced by two independent switches that may both be on: queue schedule (interval/cron) and orchestrator armed (wake interval on `orchestrationConfig`). Subtask 6 writes handoff against `orchestrationConfig` only, so subtask 4's collapse does not have to rewrite it. |

Two further outcomes:

- **Subtask 5 absorbs a non-member plan.** `feature_plan_20260817193500_orchestrator-cannot-answer-what-plans-are-ready.md` (in `CREATED`) specifies the same persona section under a different heading (`## What Is Ready To Go` vs. `## The ready set`) with its own gate assertions. Subtask 5 now adopts that plan's heading, query and assertions wholesale so there is one definition, one heading and one gate. That card is redundant and should be deleted rather than coded.
- **No merges, deletions or splits inside this feature.** The seven subtasks each own a distinct surface; the incoherence was in their contracts with each other, not in their boundaries, and it is resolved by the corrections above rather than by restructuring the set.
