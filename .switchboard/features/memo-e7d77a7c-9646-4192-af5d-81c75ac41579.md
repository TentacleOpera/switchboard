# Memo

**Complexity:** 6

## Goal

The memo file is a shared append target with two writers, an agent and the operator, and neither must destroy the others bytes. Eight cards across four features touched it. One plan now creates the shared memo module; the rest layer on it. Landing order is stated in Dependencies: watcher, then the module, then the dirty guard, then geometry, then the editor tab.

## How the Subtasks Achieve This

- **The memo modal never updates in standalone, because only one host watches the file**: Fixes the composition-root ordering bug — `_setupMemoWatcher` runs before `_hostSeams` is injected and bails on the shim's empty `workspaceFolders`. Adds a public `reinitializeMemoWatcher()` to `TaskViewerProvider` and one call in `bootstrap.ts` after `initHeadlessVerbServing`, re-arming the existing extension-proven watch → debounce → `memoUpdated` push chain. This is the live-update rail every later subtask's push depends on being armed in standalone.
- **Reviewer Risks Reach the Memo Through a Sentence, Not a Seam — Give `memo.md` a Real Append Verb**: Creates `src/services/memoFile.ts` (the one shared write module both composition roots call), adds an `O_APPEND` `memoAppend` verb wired into both `TaskViewerProvider` and the standalone inline arms, repoints `REVIEWER_RISKS_TO_MEMO_DIRECTIVE` at it (HTTP primary, shell `>>` fallback, whole-file writes forbidden), and carries the prefix-consume clear. Makes agent/reviewer appends atomic so they stop being a read-modify-write by an LLM with generic file tools — the write-side half of the two-writer safety this feature is about.
- **The Memo Panel Protects Your Typing by Throwing Away Everything an Agent Appended**: The read-side half. Replaces the dirty-guard's silent *drop* of an inbound `memoUpdated` with a prefix-check *merge* (splice the appended tail below the cursor when the incoming content still starts with the on-disk base; surface a status line, never a dialog, on a genuine conflict), and makes `memoSave` a compare-and-swap (`baseContent` opt-in, legacy clients unchanged) reusing `memoFile.ts` from the append-seam subtask. Closes the path where a typing operator silently overwrites a reviewer's just-appended risks.
- **Memo Modal Close Button Overlaps The Workspace Dropdown**: Reserves the dialog's top-right corner for the shell's `×` by deriving `--modal-close-reserve` from the button's own geometry tokens in `shell.html` and mirroring the resolved `42px` as right padding on `.memo-header` in `memo.html`. Stops the close button from swallowing clicks aimed at the workspace dropdown's caret.
- **Memo Modal Is Oversized: Dead Space Below The Memo Swallows Backdrop-Dismiss Clicks**: Sizes `#modal-dialog` to the panel's reported content height (the panel posts `documentElement.getBoundingClientRect().height`; the shell keys it per panel id, resolves on open, and compensates for the dialog border) with a 320px floor and 700px cap. Removes the ~190px of opaque dead space that swallowed the universal backdrop-dismiss click.
- **Dismiss the browser cockpit Memo modal after Copy Prompt / Send to Planner**: Adds a `__switchboardCloseModal` transport helper and a `closeModalPanel` bridge arm (origin- and source-verified, routed through `closeModal()`), schedules dismissal 600 ms after a real, locally-initiated success, and gives modal frames the `panelVisibility` signal they never had (vetoes a stale timer firing into a re-opened overlay). Returns the operator to the panel behind the overlay once a capture succeeds.

## Dependencies & sequencing (2026-09-04, Board Collapse 08)

Eight cards across four features touched one file, `.switchboard/memo.md`, which has two writers: an
agent appending and the operator typing. Land in this order.

1. **The memo modal never updates in standalone** — an ordering bug, not a missing watcher:
   `_setupMemoWatcher` runs before the host seam is injected and bails on the shim's empty workspace
   folders. Re-arm once after the seam is wired. Smallest card, unblocks observing the rest.
2. **Reviewer Risks Reach the Memo Through a Sentence** — **this plan creates
   `src/services/memoFile.ts`** and carries both the `O_APPEND` append verb and the prefix-consume,
   after *Process Memo Clears the Whole File* was merged into it and deleted. All three memo
   subtasks previously proposed creating that module under a "whichever lands first" rule, which is
   a merge hazard rather than a plan.
3. **The Memo Panel Protects Your Typing** — the dirty guard and the compare-and-swap save, built on
   the module from step 2.
4. **The three geometry fixes** — close-button overlap, then the content-sized dialog, then dismiss
   after Copy Prompt. That internal order is already stated in their own files and must be kept:
   they edit the same `#modal-dialog` rule.
5. **Memo Is the One Surface That Exists Only in the Cramped Column** — the editor tab, last.
   **Note for whoever codes it:** steps 3 and 4 add behaviour where `memo.js` posts to
   `window.parent`. In an editor-tab panel the frame **is** its own parent, so those posts must
   no-op there rather than loop. The sidebar route must also not be deleted; it is the documented
   override-immune path.

### The Memo Panel Protects Your Typing by Throwing Away Everything an Agent Appended
- **Seat:** Coder (Complexity 6)
- **Acceptance:**
  - Base `A`; user types `A + local`; `memoUpdated` arrives with `A + "\n\nB"` → textarea ends with the user's local text **and** `B`; a subsequent save writes both (today `B` is lost).
  - A non-prefix incoming content leaves the textarea untouched, sets a conflict flag and a status line, writes nothing — and there is no `confirm(`/`window.confirm(` anywhere in the new `memo.js` paths.

## Reconciliation Notes (cross-subtask audit, 2026-09-14)

The subtask set is coherent — no merge, delete, or rewrite was required (the set was already
restructured: the append-seam plan absorbed *Process Memo Clears the Whole File* and now owns
`src/services/memoFile.ts` unconditionally). Two findings a coder must carry:

1. **Line-number drift.** Every plan's line citations are stale — the source files have grown
   since the plans were written (shell.html ~40, shell.js ~150, `TaskViewerProvider.ts` ~1400,
   `bootstrap.ts` ~600–2800, `verbSchemas.ts` ~54, `agentPromptBuilder.ts` ~150,
   `transport.js` ~185). The plans quote the **full code blocks** to match by content, so they
   remain executable — locate each target by the quoted block, not by the line number. Do not
   navigate by line.

2. **The inline `bootstrap.ts` memo arms are the divergence hazard.** `planningVerb`
   (`bootstrap.ts:3896`) intercepts `memoLoad`/`memoSave`/`memoClear`/`memoGeneratePrompt` and
   `return`s early — they never reach `taskViewerProvider.handleServiceVerb`. So every memo
   server-side fix must touch **both** the inline arm **and** `TaskViewerProvider`'s arm, or it
   ships in one host and silently not the other (the exact `CLAUDE.md` precedent). The append-seam
   and dirty-guard subtasks already do this; the stale comment at `bootstrap.ts:3899`
   ("there's no TaskViewerProvider to delegate to") is wrong — one is constructed at `:1629` — and
   the append-seam subtask corrects it. Consolidating the inline arms onto `TaskViewerProvider`
   (delete the duplication, delegate) is the durable fix and is **out of scope** for this feature;
   it is a deferred follow-up, not a blocker for any subtask here.
