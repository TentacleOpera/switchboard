# Terminals Pane Resize on Layout Change

**Complexity:** 7

## Goal

Panes keep their old rendered size when the browser Terminals layout changes (e.g. 3x3 to single). Root cause: renderPaneGrid blanks the grid with innerHTML='' on every render, detaching every live xterm; xterm's RenderService parks the renderer resize and full repaint while its IntersectionObserver reports non-intersection, and rAF runs before that delivery. FitAddon.fit() then short-circuits on matching cols/rows, so the stale canvas is permanent. Subtask 1 makes the fit verify itself and retry; subtask 2 removes the DOM churn that creates the race.

**Amendment from the reconciliation pass.** The DOM churn is the *dominant* cause, not the only one. `RenderService.handleResize` opens with `if (!this._renderer.value) return;` — when no renderer is installed the resize is **dropped outright, not parked**, so nothing is left for a later intersection change to flush, while `term.resize()` has already committed the new cols/rows and disarmed `FitAddon.fit()` forever. That window is narrow but this panel deliberately creates it: `attachRenderer`'s WebGL `onContextLoss` handler swaps the WebGL addon out for the canvas one. Subtask 2 cannot close that path. Only subtask 1's verify-and-repair can — which is why subtask 1 is not merely "the symptom fix" and must ship regardless of subtask 2.

## How the Subtasks Achieve This

- **Verified Pane Fit After a Terminals-Panel Layout Change**: replaces `batchFitVisiblePanes`'s single unchecked `requestAnimationFrame` with a settle → fit → verify → resync → bounded-retry ladder (attempt 0 is a double rAF, then timers at 60/180/420 ms so a backgrounded tab still converges). The load-bearing new capability is `inspectPaneFit`, which checks *both* halves independently — the buffer (`term.cols/rows` vs `proposeDimensions()`) and the renderer (the grid actually painted, read from the live renderer's own `dimensions.css.canvas / dimensions.css.cell`). The renderer half is the one `FitAddon` cannot see and cannot repair. A generation counter supersedes in-flight ladders, `destroyTerminalView` drops the generation, the per-container `ResizeObserver` is routed through the same ladder, and a `console.warn` on give-up emits the verdict string so a field failure names its own remaining surface. This is the subtask that makes the panel self-heal from *any* stranding path, including the renderer-swap one.
- **Reconcile the Terminals Pane Grid In Place Instead of Rebuilding It**: removes the cause of the dominant path. `renderPaneGrid` stops opening with `paneGridEl.innerHTML = ''` and instead reuses pane elements — surplus panes removed, missing panes created, survivors patched in place by `updatePaneElement`. A terminal whose slot did not change never moves in the DOM, so its `IntersectionObserver` never fires, `_isPaused` never flips, and there is no race to lose. It also deletes the per-render cost that `setFocusedPane` was written to dodge: today a 9-pane grid pays a full 9-xterm detach/re-attach for an event that changed one badge label. Listeners move to a create-once `createPaneElement` and re-read `paneAssignments[index]` at call time, and the caret restore becomes conditional on the reconcile having actually taken the caret.

**Cut from the draft, deliberately:** the pixel-tolerance stale-canvas heuristic (`hostRect.width - screenRect.width > cellW + 24`) — its tolerance is smaller than the healthy baseline gap of 16 px host padding plus a ~15 px scrollbar plus up to one cell of flooring remainder, so it would have judged every layout change stale and fired the repair every time. Replaced with an exact painted-grid vs buffer-grid comparison. Also cut: the buffer-touching rows round-trip (`term.resize(cols, rows - 1)` then back), replaced by a direct `_renderService.handleResize(cols, rows)` that only reads the buffer — same effect, no `ybase` shift, and no private surface the detector did not already require.

**Settled by external research — do not re-open.** Both plans now carry a `## Resolved Assumptions` section. The headline: **upgrading xterm does not fix this.** Every release through 6.0.0 keeps the `IntersectionObserver` pause with its deferred resize task and last-record-only batch read, keeps `FitAddon.fit()`'s short-circuit with no `force` option, keeps `handleResize`'s no-renderer early return, and still exposes no public force-resize API. The `_core._renderService` surface both plans touch is shape-stable 5.1.0 → 6.0.0 (`hasRenderer()` unchanged across 5.x and 6.x) but untyped and internal, and 5.1.0 set precedent by removing flat dimension properties without deprecation — hence the defensive wrapping in subtask 1. Upstream corroboration for the defect class: xterm.js issues #3118, #3029, #2643, #4338, #4841, #5298. Separately, rAF-before-IntersectionObserver is normative, but Gecko and WebKit may defer IO *delivery* a frame under load where Chromium does not — so an attempt-0 miss on Firefox or Safari is expected, not a defect, and it is why the ladder is not rAF-only.

**Natural follow-up, out of scope here.** Research surfaced the maintainer-endorsed way to eliminate the *last* remaining churn case — a terminal moving between panes — by making terminal hosts direct grid children repositioned via `style.gridArea` rather than re-parented. That dissolves `.terminal-pane` as a container and forces the pane header and focus behaviours to be re-derived, so it is a larger restructure than subtask 2 and is recorded in that plan as deferred. The ladder's verdict logging is the trigger: if `stale-canvas` warnings cluster on assignment changes rather than layout changes, this is the next ticket.
