# Tickets panel: attachments, sync badges and push fidelity

**Complexity:** 7

## Goal

Three Tickets-panel defects found during testing, each with a distinct root cause but a shared surface: remote attachments are resolved against a per-list folder keyed on filename so they masquerade as local files; drill-down subtask cards never have their sync status requested so every badge reads 'local'; and ticket push truncates at any bare '## Subtasks' heading, silently discarding a parent ticket's own section.

A fourth subtask was added on 2026-08-08 after the original reporter confirmed none of the three above was the defect they actually reported: refetching a ticket replaces its local inline image links with remote CDN URLs that don't render. It is a different code path (import overwrite + image hosting) and is the highest-priority item in the set.

The unifying failure is the same class of mistake in four places: the panel *infers* a fact it never actually established — that a filename match means "this ticket's file", that an absent status means "local-only", that a heading means "generated by import", that a hosted URL has no local counterpart — and then presents the inference as truth with no way for the operator to tell. Grouped because they are the defect set for one panel, they touch the same small file set, and shipping them one at a time would mean four separate serialised passes over `TaskViewerProvider.ts` and `tickets.js`.

## How the Subtasks Achieve This

- **Ticket push silently drops everything below a `## Subtasks` heading, even the ticket's own**: replaces `pushTicketEdits`'s bare-heading truncation (`trimmed === '## Subtasks'`) with a shared, marker-first helper in `ticketDisplayContent.ts` — the same rule the display path already uses — plus a shape-based fallback that still withholds pre-marker legacy import blocks, and a user-visible notice when anything is withheld. Stops the panel from destroying an operator's own description text on every push.
- **Tickets panel still presents remote attachments as local files**: replaces the guessed `<listDir>/attachments/<filename>` identity with a per-ticket directory (resolved via `_findTicketDocument`) plus a provenance sidecar recorded at download time, so "is this downloaded?" is answered from what was actually downloaded for *this* ticket. Also makes the attachments modal work in the browser cockpit at all — bridging `getAttachmentList` / `downloadAttachment` into the standalone command registry (PRD Layer 2) and widening the cockpit's `img-src` so remote provider images are not blocked.
- **Subtask cards in the Tickets sidebar always read "local"**: gives the sync badge a fourth input — `undefined` means "not fetched yet", not "local-only" — folds drill-down subtask ids into the existing scope-stamped status request, splices the reply back into `_drillDownSubtasks`, and stops the local-file list rebuild from wiping resolved statuses. Turns the one badge an operator watches (`modified`) from permanently wrong into correct.
- **Refetching a ticket replaces its local inline image paths with remote URLs that don't render**: stops `hostInlineImages` discarding the local-source → hosted-URL mapping it already computes (`replacements`, currently with zero consumers anywhere), persists it into the same per-ticket sidecar, and has both import write paths map hosted URLs back to the local file before writing the `.md`. The remote keeps its CDN URLs so the ticket still renders for everyone else; only the local copy is mapped back. This is the originally-reported defect.

## Dependencies & sequencing

- **Cross-feature dependencies:** none. All four subtasks are self-contained bug fixes against shipped code; nothing from another feature must land first.
- **Shipping order:** ship **push truncation → attachments → inline-image relocalisation → sync badge**. The first three all edit `src/services/TaskViewerProvider.ts` (push at ~22067-22132, attachments at ~23507-23680, relocalisation at ~21866/~22092-22107/~22366-22427) — disjoint regions with no logical conflict, but the project PRD's orchestration discipline is one agent stream per provider file, so they must serialise. Push truncation goes first because it is the smallest, lowest-risk edit; attachments must precede relocalisation because it introduces the `_attachments.json` sidecar and its `_readAttachmentIndex` / `_recordAttachment` helpers that relocalisation reuses. The sync-badge plan shares `src/webview/tickets.js` with the attachments plan (attachments only inside `renderAttachmentsList` ~2774-2837; sync badge only in the badge helper, request builder, drill-down entry and response arms) — disjoint, mergeable in either order, but not to be edited concurrently. It is otherwise fully independent and can ship at any point if a webview-only change is wanted early.
- **Priority note:** the relocalisation subtask is the defect the reporter actually raised; the other three were found while investigating it. If only one ships, ship that one — but it depends on the attachments subtask's sidecar, so in practice the pair ships together.
- **Prerequisites / guards:** the attachments subtask carries the largest install-base risk in the set (the on-disk download destination moves, so its legacy `existsSync` fallback is what keeps ~4,000 installs' existing attachments visible) and the only cross-host obligation (the standalone bridge — without it the browser cockpit modal keeps returning `success: true` with no rows). Both must land in the same change; neither half is shippable alone. The relocalisation subtask must not revert the CDN rewrite — doing so re-breaks images for everyone reading the ticket in Linear/ClickUp, which is the bug commit `8a7e20a3` (2026-06-19) fixed. The push-truncation subtask must keep its retargeted pinning assertion in `tickets-subtask-embedding.test.js` rather than deleting it — that assertion exists specifically to stop a cleanup pass from removing the push protection.
- **Shared external question — RESOLVED 2026-08-08.** Web research settled whether Linear / ClickUp asset URLs are fetchable unauthenticated: **they are not.** Linear's `uploads.linear.app` returns 401 without a Bearer token, which an `<img>` tag cannot send; ClickUp enforces pre-signed links that expire after 60 minutes on all plans. Both affected subtasks were updated: the attachments subtask **dropped its `img-src https:` CSP widening** (it could not render provider assets and only enlarged the attack surface — `headlessPanelHtml.ts` left this plan's file set), and both subtasks switched their provenance key from the attachment **URL** to a **stable asset key**, because both providers re-sign URLs per fetch and a URL-keyed record would never match on the read side. Treat this as authoritative; do not re-research it.
