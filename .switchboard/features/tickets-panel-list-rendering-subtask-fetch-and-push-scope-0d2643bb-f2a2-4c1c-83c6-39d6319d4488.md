# Tickets Panel: List Rendering, Subtask Fetch and Push Scope

**Complexity:** 6

## Goal

Three defects in the Tickets panel, sharing the local-.md-as-source-of-truth seam. Loose-list blank lines present in the remote description are discarded by renderMarkdown's list-grouping pass and destroyed again by the editor's HTML-to-markdown round trip. Subtasks are never downloaded by any path. The fetch already returns them (`subtasks=true`) and groups them in memory, then `TaskViewerProvider.ts:23811` filters them out before anything is written, and the prune's keep-set — built from that same filtered list — deletes any subtask file that does exist. Clicking one writes nothing either: `clickupLoadTaskDetails` (`TicketsPanelProvider.ts:2542`) loads details into an in-memory cache and never touches disk. `importTicketSubtasks` (`:3031`) is not a fallback — it was intentionally unwired from the webview to stop the generated `## Subtasks` block leaking into ticket bodies, remains live over HTTP, and creates no subtask files regardless; leave it untouched. The 'Action failed: readLocalTicketFile' toast is the downstream symptom, not the bug. And Push silently means parent-only with the Subtasks block withheld, with nothing in the UI stating that scope, so an operator cannot tell whether subtask edits will be published.

## How the Subtasks Achieve This

- **Preserve Loose-List Blank Lines in Ticket Markdown Rendering and Edit Round-Trip**: Fixes the display seam at both ends. `renderMarkdown`'s list-grouping pass in `sharedUtils.js` currently consumes blank lines between bullets without recording them, and `buildListHtml` emits an unconditionally tight list — so an author's deliberate sub-group breaks render as nothing. The subtask adds a per-item `looseBefore` flag and a `md-li-loose` class, plus the CSS rule in all three panel stylesheets that inline it. It also repairs `nodeToMarkdown` in `tickets.js`, whose `ul`/`ol` serialisation flattens a loose list to a tight one *in the saved file* — without which the render fix silently un-fixes itself the first time a user edits and saves. It contributes the "what you see matches the remote" half of the feature.
- **Download Subtasks With Their Parents on Every Fetch**: Makes a subtask a real local ticket. The fetch already downloads subtasks (`subtasks=true` on the list pull) and groups them into `subtasksByParent`, then discards them at `TaskViewerProvider.ts:23887` before anything is written; the prune's keep-set, built from that same filtered list, deletes any subtask file that does exist. This subtask stops both, writes each subtask through the existing `_writeTaskDocument` with the same conflict guard, and covers the delta orphan-group path where a changed subtask arrives without its parent. It supplies the local `.md` files that the other two subtasks operate on, and it is what removes the `Action failed: readLocalTicketFile` toast.
- **Add a "Push + subtasks" Action and Make the Plain Push Button Say What It Actually Pushes**: Closes the loop by making publish scope visible and reachable. `pushTicketEdits` is single-record by construction and silently withholds the generated `## Subtasks` block, so today a parent's children are never published and the UI says nothing about it. This subtask keeps `Push` parent-only with an explicit tooltip and adds a second action that composes the existing single-ticket push over the parent plus every locally-present child — re-running the per-ticket staleness guard for each, reporting pushed/skipped/failed counts rather than a boolean. Review also found that `switchboard.pushTicketEdits` is registered only in the extension host, so `Push` is already a dead button under `npx switchboard`; repairing that registration is folded in here, since shipping a second button beside a broken one is the failure the feature is meant to remove.

## Dependencies & sequencing

- **Recommended order: loose-list rendering → subtask fetch → push scope.**
- **Hard dependency — subtask fetch MUST land before push scope.** No subtask `.md` files exist anywhere today, because the import path filters subtasks out before writing. "Push + subtasks" discovers its children by scanning local files for `parentId:` frontmatter, so without the fetch subtask it finds nothing, the new button is disabled on every ticket in the product, and none of its manual verification steps can be executed. This is the one ordering constraint that is not merely preferable.
- **Soft dependency — loose-list rendering should land before subtask fetch.** The fetch subtask creates a new population of editable files (subtask bodies), and the markdown editor's HTML→markdown round trip destroys loose-list blank lines on save. Landing the serialiser fix first means subtask files are never flattened by a user's first edit; landing it after means some files are damaged in between, and the damage is written to disk and pushable. Nothing breaks if this order is reversed — it is a data-quality window, not a functional block.
- **All three must be coded serially, not fanned out in parallel.** They touch overlapping files: `src/webview/tickets.js` is edited by all three (serialiser, `localTicketFileRead` handler, push handler/button state), `src/services/TaskViewerProvider.ts` and `src/services/TicketsPanelProvider.ts` by both the fetch and push subtasks, and `src/webview/tickets.html` by both the rendering and push subtasks. The regions are disjoint and no two subtasks rewrite the same function — but the project PRD's orchestration discipline is explicit that the same provider file serialises across agent streams. Give this feature one coder stream.
- **Prerequisite guard before starting the push subtask:** confirm subtask files actually appear on disk after a refetch. If the fetch subtask shipped but its prune keep-set change was missed, the files exist until the next full refresh and then vanish — which would make the push subtask's child discovery intermittently empty and send a coder hunting in the wrong file.
- **No contradictions or overlaps to reconcile.** A cross-subtask audit of every shared file found no duplicated work, no incompatible designs on a shared symbol, and nothing superseded: the three address independent defects (display, import, publish) that happen to meet at the same panel.

Per the dispatch, no compilation and no automated tests were run, so every plan's Verification Plan remains unexecuted — in particular the parity check on the regenerated `verbAllowlist.ts`, and all manual steps, which additionally require a VSIX rebuild because the panels are served from the installed `dist/`, not `src/`.
