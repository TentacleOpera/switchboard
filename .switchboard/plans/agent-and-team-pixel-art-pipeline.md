# Agent & Team Pixel Art: Registry, Ingest, and One Piece Wired End to End

## Goal
Make externally-generated pixel art droppable into Switchboard: a file-based art registry served to every surface, one shared resolver and CSS treatment so a piece renders identically everywhere, a small import step that turns a generator's output into a true sprite, and one role wired end to end to prove the chain. Art is then produced outside the app and committed piece by piece with no further code changes.

### The problem, and the root cause
Agent art exists today and is explicitly provisional. `kanban.html:3227` labels the block *"Placeholder art — replacing it is an edit to this block alone, no layout shift"*, and what follows is five inline `<symbol>` elements on a 24×24 viewBox with `shape-rendering="crispEdges"` (`kanban.html:3240`–`3286`): a shared head-and-body silhouette in a three-tone cyan ramp, differentiated by a 4–7 `<rect>` mark. `teamsTabPortraitId` (`kanban.html:4736`) maps `headRole` onto one of them, defaulting to `portrait-agent`. It is agent-drawn stand-in art, not a design to extend.

Three properties of how it is wired block dropping real art in:

1. **It lives inside one document.** `<use href="#portrait-lead">` resolves against the *current* document's `defs`. `kanban.html` holds the symbols; `terminals.html` and the shell rail are separate documents and cannot reference them. That is exactly why the rail draws image files from `/static/icons/` while the TEAMS tab draws inline symbols — **two parallel art pipelines that cannot share a piece.** Art added inline is invisible to the rail, the cockpit and the sidebar.
2. **There is no file-based slot for a portrait.** Team icons get one via the icon-picker plan; per-agent portraits have no path at all. A generated PNG has nowhere to go.
3. **Display sizes are not integer multiples of the grid.** `TEAMS_TAB_CELL = 28` (`kanban.html:4745`) renders a 24-unit viewBox at 28px — a 1.1667× scale. Vector rects tolerate that; **raster pixel art at a non-integer scale is visibly blurred or unevenly stepped.** Fixing the display sizes is a prerequisite for raster art of any origin, and 28 is not a useful multiple.

### The ingest trap this plan exists to handle
Art is generated by an external AI pixel-art tool. Those tools almost never emit a true sprite. Typical output is a **512×512 or 1024×1024 PNG that *depicts* pixel art** — large smooth blocks, anti-aliased block boundaries, a palette in the hundreds or thousands, and a block grid that is often fractional (e.g. 31.7 source pixels per apparent art pixel) because the generator was not working on a real grid.

Dropping that straight into a 32px slot fails in a specific and confusing way: browsers do not honour `image-rendering: pixelated` usefully when **downscaling** by a large factor. Nearest-neighbour downsampling samples one arbitrary source pixel per destination pixel, so apparent-pixel boundaries land inconsistently and the art shimmers or loses features between sizes. It looks broken while every individual asset looks fine when opened.

So the pipeline needs a one-time **import** step per asset — resample to a true 32×32 and quantise — producing a small committed sprite. This is not a drawing pipeline and requires no art skill: it is a resize with the correct algorithm.

## Approach

### 1. The input contract — the whole of what the app asks of a generated asset
Short and mechanical, so it can be checked by a script rather than read as a style guide:
- **32×32 pixels**, RGBA, transparent background.
- **Hard edges** — no anti-aliased or semi-transparent boundary pixels (they read as blur once scaled up).
- Nothing else is prescribed. Palette size, colour choices, silhouette and style are the generator's business.

Non-conforming input is expected to be the norm, which is what step 2 is for. The contract describes the *output* of import, not what the generator must produce.

### 2. Import: one script, run per asset, output committed
`scripts/import-pixel-art.mjs` — takes any raster, emits a conforming 32×32 PNG:
1. Trim fully-transparent margins.
2. Detect the apparent block grid (modal run-length of colour changes along both axes). Fall back to a `--grid=N` override when detection is ambiguous, and **report** what it detected rather than silently guessing.
3. Resample to 32×32 by **area-averaging one apparent block to one output pixel**, not nearest-neighbour — averaging within a block is what removes the generator's anti-aliasing instead of sampling into it.
4. Quantise, snapping near-identical colours together, and hard-threshold alpha to fully opaque or fully transparent.
5. Write `icons/pixel/<kind>/<id>.png` and print the resulting palette size and dimensions.

Run it by hand per asset and commit the output. **Do not** wire it into `npm run compile`: `dist/` is not used in development or testing per CLAUDE.md, the inputs are one-off, and a build step that rewrites committed art would fight the very reproducibility that committing it buys. If the generator can already emit a true 32×32, skip the script entirely — it is a convenience, not a gate.

Keep the original generator output out of the repo, or under `design_system/` if worth keeping; only the imported sprite ships.

### 3. The registry — files plus a manifest
```
icons/pixel/
  manifest.json
  agents/<role>.png          # lead.png, coder.png, planner.png, reviewer.png, agent.png
  teams/<slug>.png
```
`manifest.json` entries: `{ id, kind: 'agent'|'team', label, src, grid: 32, version }`.

**Consumers reference `id`, never a path.** This is the load-bearing decision: a stored `art:<id>` survives regenerating a piece, renaming a file, or restructuring the directory. Team icons chosen during the placeholder period keep working when the art under them is replaced — that is why the icon-picker plan stores `art:` ids rather than filenames. Regenerating art from a better prompt is expected to happen repeatedly, so this property matters more here than it would with hand-drawn assets.

Delivery needs no new route: `/static/icons/` already maps to `icons/` in both hosts (`TaskViewerProvider.ts:3522`, `bootstrap.ts:672`) and normalises nested relative subpaths (`LocalApiServer.ts:906`), so `/static/icons/pixel/agents/lead.png` works today. Static art is cached `public, max-age=3600` (`LocalApiServer.ts:920`) — carry `version` in the manifest and append it as a query param so a regenerated piece is not served stale for an hour. Given how often assets will be re-rolled, this is the difference between "the new art didn't work" and "the new art appeared".

### 4. One resolver, one CSS class, five surfaces
- `resolveArt(idOrValue)` → `{ src, grid }` or `null`. The single place an `art:` id, a `pack:` filename or a `data:` URI becomes a URL. The icon-picker plan specifies `teamIconSrc` as this seam; extend that function rather than adding a second one.
- One CSS class, defined once per webview stylesheet (they are separate documents; there is no shared sheet):
  ```css
  .pixel-art { image-rendering: pixelated; -ms-interpolation-mode: nearest-neighbor; }
  ```
- **Integer display sizes only: 32px and 64px.** 32 for the shell rail, flow nodes and sidebar rows; 64 for gallery cards and the cockpit header. Set explicit `width`/`height` plus `flex: none` — a flex parent that stretches the `<img>` to a fractional box silently reintroduces the blur the import step exists to remove.
- **`TEAMS_TAB_CELL` changes 28 → 32.** A real layout change to the TEAMS gallery; verify the card grid does not reflow badly. The constant's comment says it is fixed *"so better art cannot shift layout"* — preserve that intent at the new value.
- Render with `<img>`, not the CSS-mask/`currentColor` path used for nav icons. The reasoning is recorded at `shell.js:542`: multi-hue art whose baked-in fill *is* the identity, and masking flattens it to one colour.
- Apply at: TEAMS gallery card (`kanban.html:4800`), TEAMS flow head node (`kanban.html:4924`), shell rail button, team cockpit header, cockpit sidebar rows.

### 5. Per-agent art, replacing `teamsTabPortraitId`
Resolve a role through the registry: `agents/<role>.png` when present, else the inline `<symbol>`, else `portrait-agent`. Keep `teamsTabPortraitId` as the fallback arm rather than deleting it — a half-populated set must not leave blank cards, and roles are operator-authored free text (`members[].role`, `kanban.html:5315`), so an unknown role is the normal case, not an error.

Allow a per-role art override in the agent config so a custom role can point at an existing piece without editing the registry.

### 6. Rollout
1. Registry, manifest, resolver, CSS, `TEAMS_TAB_CELL` → 32, import script, fallback chain. **No art required** — every surface renders as it does today because each piece falls back to its inline symbol.
2. Generate and import one piece — `agents/lead.png`. Confirm it renders at 32px in the rail and 64px on the card with hard edges, while the other four roles still show placeholders. This is the end-to-end proof and a sensible end to this week's work.
3. Asset production continues outside the app. Each committed sprite lights up everywhere at once, no code change.

This ordering front-loads the code so art can arrive whenever it is generated, and lets the stand-in sci-fi pack drop out of the icon picker's palette as soon as the manifest carries real pieces.

## Edge cases
- **Generator emits a large anti-aliased image and it is committed unimported.** The likeliest mistake, and it looks like a rendering bug rather than a bad asset. Add a check — in the manifest loader in dev mode, or as a lint script — that flags any `icons/pixel/**` PNG that is not 32×32, naming the import script. Fail loudly at the source rather than shipping shimmering art.
- **Grid detection fails.** Generated art with dithering, gradients or noise has no clean modal run length. The script must say so and require `--grid=N` rather than producing a plausible-looking wrong result.
- **Piece in the manifest, missing on disk.** `<img>` 404s. Give every art `<img>` an `onerror` that falls through the chain, so a stale manifest degrades to placeholders rather than broken-image glyphs.
- **Non-integer rendered box.** Add a dev-mode assertion logging when a rendered art element's computed box is not 32 or 64. Subtle and easy to reintroduce during unrelated CSS work.
- **High-DPI displays.** `pixelated` at a 2× device ratio maps each art pixel to an even number of device pixels, which is correct. Do **not** ship `@2x` variants — one asset serves every ratio. Verify on Retina.
- **Light theme.** Generated art will be prompted against one background in practice. Check each piece on both themes; where a piece disappears, the fix is regenerating or a container chip behind the mark, not a per-theme asset pair.
- **Id space collision between agent and team art.** One manifest, one id space. Either prefix by kind (`agent:lead`, `team:foo`) or require globally unique ids with `kind` authoritative. Pick one and state it in the manifest schema — an ambiguous id space is how the two icon pipelines diverged in the first place.
- **Operator supplies a non-pixel image as a custom team icon.** The `data:` form accepts any raster and bypasses import entirely. Render it with `pixelated` anyway (harmless at 1×) and note in the picker that 32×32 is expected. Do not detect or reject.
- **Inline symbols orphaned.** Once every role has art the `<symbol>` block is dead weight in `kanban.html`. Remove it in a separate change together with the fallback arm, not as a drive-by deletion.

## Verification Plan
1. `npm run compile` — clean.
2. Import script, on a real generator output: a 1024×1024 anti-aliased "pixel art" PNG imports to a 32×32 sprite with hard edges and a small palette. Compare against a nearest-neighbour downscale of the same input to demonstrate the difference the area-averaging step makes — this is the claim the script exists on.
3. Import script: reports detected grid; refuses rather than guessing when detection is ambiguous; honours `--grid=N`.
4. Lint/check: a non-32×32 file under `icons/pixel/**` is flagged with the import script named in the message.
5. Unit: `resolveArt` — `art:<id>` hits the manifest; unknown id returns `null`; `pack:` and `data:` forms still resolve (icon-picker cases must not regress); `version` is appended.
6. Unit: role → art resolution walks registry → inline symbol → `portrait-agent`; an unknown operator-authored role lands on `portrait-agent` without throwing.
7. Unit/DOM: every art element's **computed** box is exactly 32 or 64 CSS px in all five surfaces.
8. Manual, installed VSIX, **no art present**: TEAMS gallery, flow diagram, rail, cockpit header and sidebar are visually unchanged from today apart from the 28→32 portrait size, and the card grid does not reflow badly.
9. Manual: add `agents/lead.png`, reload. It appears in all five surfaces. Zoom to 400% — hard pixel edges, no interpolation. Other four roles still show placeholders.
10. Manual: regenerate `lead.png`, bump `version`, reload — new art appears immediately, not after the 1-hour cache window.
11. Manual: delete `lead.png` while still in the manifest — every surface falls back, no broken images, no console spew.
12. Manual: one piece on Retina at 32 and 64, on both themes.
13. Manual: set a team icon to an `art:` id, then regenerate the PNG and change its `src` in the manifest — the team's icon still resolves. The placeholder-swap guarantee the registry exists for.
