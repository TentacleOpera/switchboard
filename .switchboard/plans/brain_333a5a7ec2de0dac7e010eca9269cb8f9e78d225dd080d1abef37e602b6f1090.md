# Unix Domain Sockets in Sandboxed AI Coding Environments

## Executive Summary

Sandboxed shell environments used by AI coding agents and execution engines do not treat Unix domain sockets and TCP loopback connections identically. The isolation of Unix domain sockets depends directly on the underlying sandboxing paradigm. On Linux-based container and namespace sandboxes (such as Bubblewrap, Docker, Podman, and nsjail), network isolation via network namespaces (`CLONE_NEWNET`) strictly blocks direct IP loopback (TCP `127.0.0.1`) and abstract Unix domain sockets, but does not block filesystem-bound Unix domain sockets. Because filesystem-bound Unix sockets are resolved through the Virtual Filesystem (VFS) and Mount Namespaces rather than the network stack, standard Linux network sandboxing allows them as long as the socket inode is mounted and accessible within the sandbox filesystem view.

Conversely, on macOS platforms utilizing the Seatbelt (`sandbox-exec` / SBPL) Mandatory Access Control framework—such as Claude Code and Cursor on macOS—network restrictions operate through unified kernel MAC hooks that govern socket system calls regardless of transport. In these environments, broad network denial policies routinely intercept and block both TCP loopback and Unix domain socket connections (`connect()`, `bind()`) unless explicit socket-level allow rules or global Unix socket bypass flags are configured. Furthermore, application-level kernel virtualization runtimes such as gVisor (`runsc`) intercept all socket system calls in userspace and block host Unix domain socket communication by default unless specialized host proxy flags (`--host-uds=all`) are enabled.

For local agent-to-host tooling architectures like Switchboard, transitioning from TCP `127.0.0.1` to filesystem-bound Unix domain sockets significantly improves compatibility in Linux namespace environments (bwrap, Docker volume mounts, unshare). However, Unix sockets do not provide an unconditional, zero-configuration drop-in across all agent sandboxes. On macOS Seatbelt runtimes and strict gVisor/microVM sandboxes (like E2B or Cloud VM sandboxes), Unix sockets remain blocked or inaccessible across the boundary. A fully resilient architecture should employ Unix domain sockets as a primary low-latency transport alongside an atomic file-based polling or stdio fallback for strictly isolated environments.

## Platform Findings

### Anthropic Claude Code
- **Status and Capability:** Claude Code implements dual-engine sandboxing depending on the host OS. On macOS, it utilizes Apple Seatbelt (`sandbox-exec`), while on Linux and WSL2, it utilizes Bubblewrap (`bwrap`). In its default sandboxed execution profile, outbound TCP connections to `127.0.0.1` / `localhost` are blocked via proxy isolation and firewall filtering to prevent Server-Side Request Forgery (SSRF) and host service compromise.
- **Unix Domain Socket Behavior:** On macOS Seatbelt, Unix domain socket access is blocked by default under the restrictive security profile. On Linux Bubblewrap, access to host Unix sockets depends on whether the socket path resides within a mounted filesystem path. Anthropic explicitly added sandbox configuration directives in `settings.json` (`sandbox.network.allowUnixSockets` for specific socket paths and `sandbox.permissions.allowAllUnixSockets: true` for wildcard socket creation/connection) to unblock tools such as the Nx daemon, Playwright, and MSBuild.
- **Known / Unknown:** Known: Unix domain sockets are blocked by default on macOS and restricted by path on Linux; `allowAllUnixSockets` or explicit allowlists resolve the block. Unknown: Exact internal SBPL profile evolution across upcoming Claude Code desktop releases.
- **Confidence Level:** High (Confirmed via official documentation, configuration schema, and vendor release notes).

### Cursor IDE Terminal Sandbox
- **Status and Capability:** Cursor employs sandboxing for terminal command execution and background agent processes, leveraging macOS Seatbelt and Linux container namespaces. By default, local network connections to `127.0.0.1` are restricted to prevent unauthorized host interaction and network exfiltration.
- **Unix Domain Socket Behavior:** On macOS, Seatbelt rules enforce socket-level denials that intercept `connect()` calls to Unix sockets residing outside the immediate workspace directory. Users encountering blocked IPC daemons (such as language servers, local database sockets, or Docker sockets) must update `~/.cursor/sandbox.json` to configure read/write paths or set network policies to permit specific socket paths.
- **Known / Unknown:** Known: Unix domain sockets outside the workspace root are inaccessible without configuration. Unknown: Internal schema changes planned for Cursor's background agent isolation layer.
- **Confidence Level:** High (Confirmed via developer community debugging reports and sandbox configuration structures).

### OpenHands (formerly OpenDevin)
- **Status and Capability:** OpenHands executes agent workflows within Docker containers. By default, Docker containers operate in an isolated network namespace (`bridge` or custom network), meaning `127.0.0.1` inside the container refers to the container's own loopback interface, not the host machine.
- **Unix Domain Socket Behavior:** When containers run with restricted network configurations (including `--network none`), filesystem-bound Unix domain sockets mounted from the host via volume binds (`-v /path/to/socket.sock:/path/to/socket.sock`) work reliably. Standard container seccomp profiles allow `socket(AF_UNIX, ...)`, enabling full IPC between the agent inside the container and a host-side daemon.
- **Known / Unknown:** Known: Host TCP loopback is unreachable without host gateway routing (`host.docker.internal`), but volume-mounted Unix sockets function without network permissions.
- **Confidence Level:** Very High (Confirmed via Docker engine specifications and OpenHands container architecture).

### E2B Sandboxes (Firecracker MicroVMs)
- **Status and Capability:** E2B provides isolated cloud sandboxes running inside AWS Firecracker microVMs with dedicated guest Linux kernels.
- **Unix Domain Socket Behavior:** Because Firecracker microVMs operate at the hardware virtualization boundary (KVM) with separate guest kernels and filesystems, host Unix domain sockets cannot be shared directly via filesystem mounts. Communication between host and guest requires either virtual socket devices (`AF_VSOCK`), network bridge routing, or E2B's gRPC/HTTPS management protocol.
- **Known / Unknown:** Known: Host filesystem Unix sockets are physically isolated by the VM boundary; `AF_UNIX` sockets can only operate internally between processes inside the same microVM.
- **Confidence Level:** Very High (Confirmed via Firecracker architectural specifications and E2B runtime documentation).

### Aider & Community Jailed Agents
- **Status and Capability:** Aider executes directly on the host machine by default without process confinement. However, security-conscious deployments and wrappers (such as `jailed-agents` and community scripts) enclose Aider in Bubblewrap or Firejail sandboxes.
- **Unix Domain Socket Behavior:** In community Bubblewrap configurations using `--unshare-net`, filesystem-bound Unix domain sockets within bind-mounted directories function seamlessly, whereas abstract Unix domain sockets and TCP `127.0.0.1` traffic are isolated.
- **Known / Unknown:** Known: Aider has no native sandbox to block sockets; external sandbox wrappers follow standard Linux namespace rules.
- **Confidence Level:** High (Confirmed via Aider repository analysis and community sandbox configurations).

### Windsurf / Codeium Cascade
- **Status and Capability:** Windsurf runs shell tools in managed sub-environments with strict workspace directory scoping and execution controls.
- **Unix Domain Socket Behavior:** Local loopback TCP connections to unapproved ports trigger permission prompts or environment restrictions. Filesystem Unix sockets located within the active project workspace root are accessible via standard file operations, whereas system-wide socket paths (e.g., `/var/run/`) are restricted by workspace boundary sandboxing.
- **Known / Unknown:** Known: Workspace-local paths are prioritized; arbitrary system sockets are restricted.
- **Confidence Level:** Medium-High (Confirmed via platform behavior and developer testing).

### SWE-agent / SWE-bench Execution Environments
- **Status and Capability:** Benchmark execution harnesses enforce sandboxed command evaluation using Docker containers to prevent evaluated models from contaminating host benchmarks or exfiltrating evaluation sets.
- **Unix Domain Socket Behavior:** The evaluation containers isolate network namespaces. Volume-mounted Unix domain sockets function without requiring network interface activation.
- **Known / Unknown:** Known: Linux kernel socket operations function over mounted volume paths.
- **Confidence Level:** Very High (Confirmed via SWE-bench Dockerfiles and benchmark runtimes).

## Sandbox Mechanism Analysis

### Linux Namespaces: Network vs. Mount Isolation
The Linux kernel enforces a clear division between network namespaces (`CLONE_NEWNET`) and mount namespaces (`CLONE_NEWNS`):
- **Abstract Unix Sockets:** Sockets initialized with a leading null byte (`\0`) in the address structure (`sockaddr_un.sun_path`) do not create an inode in the Virtual Filesystem (VFS). Instead, they exist entirely within the kernel's network subsystem. Consequently, when a sandbox invokes `unshare(CLONE_NEWNET)` or `--unshare-net`, abstract Unix sockets on the host become completely invisible and unreachable to sandboxed processes.
- **Filesystem-Bound Unix Sockets:** Sockets bound to concrete filesystem paths (e.g., `/tmp/switchboard.sock` or `.switchboard/api.sock`) create an inode with file type `S_IFSOCK`. When a sandboxed process invokes `connect()` on a pathname, the kernel performs pathname resolution through the process's Mount Namespace and VFS directory hierarchy. The network namespace is not consulted for path resolution. Therefore, a process in a completely isolated network namespace (`--network none` or `CLONE_NEWNET` with no interfaces configured) can successfully connect to an `AF_UNIX` socket as long as the socket inode is present in its mount tree and permissions (`chmod`/`chown`) permit access.

### Seccomp-BPF Filtering
Seccomp-BPF (Secure Computing with Berkeley Packet Filters) allows parent processes to filter or restrict system calls executed by children:
- **Default Profiles:** The standard OCI / Docker seccomp profile, systemd default filters, and container runtimes explicitly permit the `socket` syscall with argument `family == AF_UNIX` (1).
- **System Necessity:** `AF_UNIX` is required by virtually all standard Linux userland libraries and system runtimes, including `glibc` name service switches (`nsswitch`), `getpwnam()`, syslog logging (`/dev/log`), and internal standard library IPC. Blocking `socket(AF_UNIX, ...)` unconditionally breaks core language runtimes (Python, Node.js, Ruby) and basic shell utilities.
- **Filtering Potential:** While seccomp can inspect system call arguments to block `socket(AF_INET, ...)` or `socket(AF_INET6, ...)` while allowing `AF_UNIX`, it cannot inspect deep pointer structures to filter specific filesystem paths passed to `connect()`. Path-level filtering in Linux is delegated to mount namespaces and LSMs (AppArmor/SELinux).

### Bubblewrap (bwrap) Confinement
Bubblewrap is the standard unprivileged sandboxing tool for desktop and agent environments on Linux:
- **Network Isolation:** Invoking `bwrap --unshare-net` creates a new network namespace containing only an unconfigured loopback interface, completely disabling host TCP/UDP communication (including `127.0.0.1`).
- **Filesystem Binding:** Bubblewrap builds an explicit mount namespace from scratch. By default, host directories are hidden unless explicitly mapped using `--bind`, `--ro-bind`, or `--dev-bind`.
- **Unix Socket Interaction:** If a directory containing a Unix domain socket (such as the repository's `.switchboard/` directory or `/tmp`) is bind-mounted into the Bubblewrap container, the sandboxed process can open and connect to that socket without requiring any network permissions. `curl --unix-socket /path/to/socket.sock http://localhost/` succeeds natively under `bwrap --unshare-net --bind $(pwd) $(pwd)`.

### macOS Seatbelt (sandbox-exec / SBPL)
Apple's Seatbelt framework enforces Mandatory Access Control through compiled Scheme-based sandbox profiles:
- **Unified Policy Engine:** Unlike Linux, macOS Seatbelt evaluates both network transport and IPC under broad security rules. When a profile specifies `(deny network*)` or `(deny default)`, all socket operations are restricted at the kernel MAC hook layer (`mpo_socket_check_connect`, `mpo_socket_check_create`).
- **Unix Domain Socket Restrictions:** In strict Seatbelt profiles, opening or connecting to a Unix domain socket fails with `EPERM` (Operation not permitted) even if the file is readable and writable in the filesystem. To permit Unix domain socket communication, the SBPL profile must explicitly include rules such as:
  ```scheme
  (allow network-outbound (literal "/path/to/socket.sock"))
  (allow network-bind (literal "/path/to/socket.sock"))
  ```
- **Agent Sandbox Configuration:** In tools like Claude Code on macOS, because the underlying Seatbelt profile denies general network/IPC by default, the agent runtime must translate configuration directives (`allowUnixSockets`) into explicit SBPL allow clauses when spawning the sandboxed shell process.

### gVisor (runsc) Virtualization
gVisor provides an application kernel written in Go (the Sentry) that intercepts application system calls via ptrace or KVM:
- **Syscall Emulation:** The Sentry implements its own network stack (netstack) and internal virtual filesystem. By default, it does not forward raw socket system calls to the host Linux kernel.
- **Host UDS Forwarding:** For a sandboxed process inside gVisor to connect to a Unix domain socket hosted on the host machine, the gVisor filesystem proxy (Gofer) must mediate the connection. This requires the runtime argument `--host-uds=all` or `--host-uds=open`. Without this explicit flag, `connect()` to a host Unix socket returns `EACCES` or `ECONNREFUSED`.

### nsjail and Firejail
- **nsjail:** Combines user, network, mount, PID, and IPC namespaces with Kafel seccomp policies. Network isolation isolates `AF_INET`/`AF_INET6` and abstract sockets. Path-based `AF_UNIX` sockets operate across the namespace boundary provided the socket path is included in the mount configuration (`--bindmount`).
- **Firejail:** Supports `--net=none` to isolate IP networking. Unix sockets in `/tmp` or the home directory remain accessible unless blocked by filesystem security profiles (`--private-etc`, `--private-tmp`, or path blacklisting).

## Alternative IPC Mechanisms

When both TCP loopback and Unix domain sockets are restricted or cross-environment boundaries prevent direct socket connections, the following alternative IPC mechanisms provide varying degrees of compatibility and complexity.

### 1. Atomic File-Based Polling and Request-Response Queues
- **Mechanism:** The host server and the sandboxed agent communicate via regular files placed in a shared directory that the agent already has permission to read and write (such as `.switchboard/ipc/` inside the active workspace).
- **Operation:**
  1. The agent writes a JSON request payload to `.switchboard/ipc/requests/req-<uuid>.tmp` and atomically renames it to `.switchboard/ipc/requests/req-<uuid>.json`.
  2. The host API server watches the directory (using inotify / kqueue / fs.watch) or polls it, processes the request, writes the response to `.switchboard/ipc/responses/res-<uuid>.json`, and atomically updates an index.
  3. The agent reads the response file and unlinks the processed request.
- **Sandbox Compatibility:** Exceptional. Any sandbox that permits basic file writing to the workspace (which all coding agents require to edit code) natively supports this pattern without requiring socket syscalls, network permissions, or seccomp modifications.
- **Limitations:** Higher latency (1-10ms depending on polling interval vs. sub-millisecond for sockets); requires filesystem cleanup routines to purge orphaned files.

### 2. Standard Input/Output Pipes (stdio Subprocess Bridge)
- **Mechanism:** Communication occurs directly across process stdio streams (`stdin`/`stdout`/`stderr`) using JSON-RPC or length-prefixed protocol frames.
- **Operation:** The parent process spawns the agent or a lightweight helper CLI tool, communicating through standard anonymous pipes created prior to sandbox confinement.
- **Sandbox Compatibility:** Universal. Anonymous pipes created before entering `sandbox-exec`, `bwrap`, or container isolation inherit open file descriptors that bypass subsequent namespace and network restrictions.
- **Limitations:** Requires a direct parent-child process relationship; unsuitable for decoupled background daemons that agents need to reach ad hoc via independent shell commands like `curl`.

### 3. Named Pipes (FIFOs / mkfifo)
- **Mechanism:** Inter-process communication via filesystem FIFO special files created with `mkfifo`.
- **Operation:** A pair of named pipes (`request.pipe` and `response.pipe`) is created in a shared directory for half-duplex request and response streaming.
- **Sandbox Compatibility:** Moderate to High. Bypasses network namespaces on Linux, but may be blocked by sticky directory protections (`fs.protected_fifos = 2`), certain strict seccomp profiles blocking `mknod`/`mkfifo`, or macOS Seatbelt `(deny file-write*)` rules that exclude special files.
- **Limitations:** Fragile error recovery; blocking open/read semantics require careful concurrency handling to prevent agent deadlocks if the host server restarts.

### 4. POSIX Shared Memory and System V IPC
- **Mechanism:** Memory regions shared across processes via `shm_open`, `mmap`, or `shmget`.
- **Sandbox Compatibility:** Very Low. Isolated by IPC namespaces (`CLONE_NEWIPC`) in Linux containers and explicitly denied by macOS Seatbelt `(deny ipc-posix*)` in default profiles.
- **Limitations:** Extremely high implementation complexity; requires synchronization primitives (semaphores, mutexes) that are also frequently blocked in sandboxes.

### 5. MicroVM Virtual Sockets (AF_VSOCK)
- **Mechanism:** Hypervisor-level communication protocol for microVM sandboxes (Firecracker, QEMU, Cloud Hypervisor).
- **Sandbox Compatibility:** Dedicated to VM environments. Allows guest processes to communicate with the host without IP network configuration.
- **Limitations:** Requires specialized kernel support and hypervisor configuration; not applicable to standard OS process sandboxes (Seatbelt/bwrap).

## Trade-off Evaluation

| Dimension | Unix Domain Sockets | Loopback TCP (127.0.0.1) | Atomic File Polling | Stdio Subprocess RPC | Named Pipes (FIFOs) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Linux Sandbox Compatibility** | **High** (Bypasses `CLONE_NEWNET` if path mounted) | **Low** (Blocked by `CLONE_NEWNET` & `--unshare-net`) | **Universal** (Only requires workspace write) | **Universal** (Inherited file descriptors) | **Medium-High** (Requires FIFO support) |
| **macOS Sandbox Compatibility** | **Medium** (Blocked by strict Seatbelt unless allowed) | **Low** (Blocked by default Seatbelt & firewall) | **Universal** (Standard file operations allowed) | **Universal** (Bypasses MAC policy) | **Medium** (Subject to special file MAC rules) |
| **gVisor / MicroVM Compatibility** | **Low** (Requires `--host-uds=all` or vsock) | **Low** (Requires guest network bridge) | **High** (Works over shared 9P / virtio-fs) | **Universal** (Host-managed runner) | **Low** (Filesystem emulation issues) |
| **Tooling & CLI Ergonomics** | **High** (`curl --unix-socket`, standard HTTP) | **Very High** (Standard `curl http://127.0.0.1:port`) | **Medium** (Requires helper script or JSON files) | **Low** (Cannot invoke via arbitrary CLI) | **Medium** (Shell redirection `cat > fifo`) |
| **Latency & Performance** | **Ultra-Low** (< 0.1ms, zero-copy kernel buffer) | **Low** (0.2 - 0.5ms TCP stack overhead) | **Medium** (1.0 - 10ms filesystem / polling) | **Ultra-Low** (< 0.1ms direct pipe) | **Ultra-Low** (< 0.1ms kernel pipe buffer) |
| **Concurrency & Multiplexing** | **High** (Standard HTTP/1.1 & HTTP/2 pooling) | **High** (Standard HTTP connection pooling) | **Medium** (Requires UUID-based file tracking) | **Low** (Single channel per process pair) | **Low** (Requires separate pipes per client) |
| **Security Attack Surface** | **Low-Medium** (Filesystem permission governed) | **Medium-High** (Risk of SSRF, port scanning) | **Minimal** (Confined entirely to project root) | **Minimal** (Private process memory) | **Low** (Filesystem permission governed) |

### Recommended Architectural Strategy
1. **Primary Interface:** Implement a Unix domain socket HTTP listener (e.g., `.switchboard/switchboard.sock` within the project root). This provides seamless, high-performance compatibility with `curl --unix-socket` across standard Linux sandboxes (Bubblewrap, Docker volume mounts, nsjail) without triggering network loopback alarms or requiring sandbox bypass flags.
2. **macOS & Claude Code Configuration:** Document and export sandbox configurations for Claude Code (`sandbox.network.allowUnixSockets: [".switchboard/switchboard.sock"]`) and Cursor to ensure the Seatbelt profile allows the path without requiring global network bypass.
3. **Resilient Fallback:** Provide a file-based request/response queue in `.switchboard/ipc/` as an automatic fallback for ultra-strict sandboxes (macOS locked-down Seatbelt, gVisor without host-uds, and cloud microVMs) where all socket system calls are denied.

## Glossary

- **Abstract Unix Socket:** A Linux-specific Unix domain socket whose address structure begins with a null byte (`\0`). It exists purely in kernel memory within the network namespace and has no corresponding filesystem inode.
- **Filesystem-Bound Unix Socket:** A standard POSIX Unix domain socket (`AF_UNIX` / `AF_LOCAL`) bound to an explicit path in the Virtual Filesystem (`S_IFSOCK` inode).
- **Network Namespace (`CLONE_NEWNET`):** A Linux kernel isolation feature that virtualizes network devices, IP routing tables, port bindings, and abstract Unix sockets.
- **Mount Namespace (`CLONE_NEWNS`):** A Linux kernel isolation feature that provides an isolated list of mounted filesystems and directory hierarchies.
- **Seatbelt (SBPL):** Apple's kernel-level Mandatory Access Control framework (historically driven via `sandbox-exec` and `.sb` profiles) that restricts system calls based on declarative security policies.
- **Seccomp-BPF:** A Linux kernel security facility that filters system calls using Berkeley Packet Filter programs evaluated at system call entry.
- **gVisor (runsc):** A user-space application kernel developed by Google that isolates containerized applications by intercepting and emulating Linux system calls.
- **Bubblewrap (`bwrap`):** An unprivileged Linux sandboxing utility that leverages user namespaces, mount namespaces, and network namespaces to construct minimal execution sandboxes.
- **Firecracker:** An open-source virtualization technology developed by AWS that uses KVM to launch minimalist microVMs for serverless and agent isolation.
- **SO_PEERCRED:** A socket option on Unix domain sockets that allows a receiving server to securely retrieve the credentials (PID, UID, GID) of the connecting peer process.
