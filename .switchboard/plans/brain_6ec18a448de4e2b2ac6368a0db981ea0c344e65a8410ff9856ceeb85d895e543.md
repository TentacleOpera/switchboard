# Natural Content Height Measurement in Embedded Documents

## Executive Summary

When an iframe's viewport is taller than its contained document (for example, a 700px fixed-height dialog iframe hosting a 510px panel document), `document.documentElement.scrollHeight` **fails** to return the natural content height. Under section 6.1 of the CSSOM View Module specification, reading `scrollHeight` on the root element (`<html>`) in standards mode normatively evaluates to `max(viewport_height, scrolling_area_height)`. Consequently, `documentElement.scrollHeight` returns `700px` rather than `510px` across Chromium, Gecko, and WebKit.

The true natural content height can only be measured using `document.documentElement.getBoundingClientRect().height` (or `document.body.getBoundingClientRect().height` when `body` carries `margin: 0`), provided `<html>` has default `height: auto` and no explicit height or flex/grid stretch constraints. Observing layout changes via `ResizeObserver` attached to `document.documentElement` reliably detects descendant mutations—including `resize: vertical` textarea drags and scrollbar toggles. Calling `window.parent.postMessage(msg, targetOrigin)` with a mismatched origin silently aborts delivery without throwing an exception. To detect if a document is embedded cross-origin, checking `window.parent === window` is completely safe and non-throwing, whereas reading `window.frameElement` throws a `SecurityError` `DOMException`.

## Required Findings

### 1. Root Element scrollHeight Semantics

#### Spec Definition
Section 6.1 of the CSSOM View Module specification defines the `scrollHeight` getter on `Element`. Step 1 and Step 2 lay down the normative algorithm for document root elements:

> "1. Let viewport height be the height of the viewport.  
> 2. If element is the root element and document is in standards mode: return the maximum of viewport height and the scrolling element's scrolling area height."

Because `scrollHeight` is defined as `max(viewport_height, scrolling_area_height)`, whenever the viewport height (e.g., the 700px iframe container height) exceeds the content height (e.g., 510px), `document.documentElement.scrollHeight` evaluates to `700px`. It acts as a viewport floor and cannot measure content shrinking or unconstrained natural height smaller than the iframe.

#### Engine Divergence & Implementation Audit
- **Chromium (Blink)**: Implements the spec exact algorithm in `Element::scrollHeight()`. When standards mode `<!DOCTYPE html>` is present, `document.documentElement.scrollHeight` floors at `LayoutView` layout viewport height.
- **Gecko (Firefox)**: Implements the spec exact algorithm in `nsGenericHTMLElement::ScrollHeight()`.
- **WebKit (Safari)**: Implements the spec exact algorithm in `Element::scrollHeight()`.

All three engines behave identically in standards mode: `document.documentElement.scrollHeight` returns `max(viewport, content)`.

#### Standards Mode vs. Quirks Mode
In Quirks Mode (documents missing `<!DOCTYPE html>`), the scrolling element behavior historically transferred to `document.body`. Under modern `document.scrollingElement` specs:
- In Quirks Mode, `document.body.scrollHeight` carries the `max(viewport, content)` behavior, whereas `document.documentElement.scrollHeight` returns `document.documentElement.clientHeight`.
- In Standards Mode, `document.scrollingElement` points to `document.documentElement`, which enforces the `max(viewport, content)` rule.

### 2. Root Element Layout & getBoundingClientRect Height

#### Spec Definition & Layout Model
Under CSS 2.2 and CSS Box Model Level 3, the root element (`<html>`) establishes the root block formatting context. When `html` has `height: auto` (the default value):
- Its used height is calculated based on the height of its flow children (primarily `<body>`).
- It does **not** automatically stretch to fill the viewport (Initial Containing Block).

`document.documentElement.getBoundingClientRect().height` returns the layout border-box height of the `<html>` element in device pixels (as a floating-point number). If the document content requires `510px`, `document.documentElement.getBoundingClientRect().height` returns `510.0` regardless of whether the iframe viewport is 100px, 700px, or 2000px tall.

#### Conditions Under Which Root Height Stretches
The root element's used height becomes equal to or bounded by the viewport height under any of the following CSS conditions:
1. **Explicit Percentage Height**: `html { height: 100% }` resolves against the Initial Containing Block (viewport height), forcing `<html>` to stretch to 700px.
2. **Viewport Units**: `html { min-height: 100vh }` forces used height to be at least 700px.
3. **Flexbox / Grid Root Container**: Placing `display: flex` or `display: grid` on `html` or formatting context children that force stretch.
4. **Propagated Overflow**: If `html` or `body` specifies overflow rules that alter box sizing or scrollbar gutters.

#### Margin Collapsing Between Root and Body
By CSS 2.2 section 8.3.1, top and bottom margins of `document.body` collapse with `document.documentElement` margins **unless**:
- `documentElement` has padding or borders.
- `documentElement` establishes a new block formatting context.

When `body` carries default browser margins (typically `8px`), and `html` has no padding/border, the top and bottom margins collapse outside `html` or expand `html`'s box. When `body` has `margin: 0` explicitly set, margin collapsing between `html` and `body` is completely eliminated. Consequently, `document.documentElement.getBoundingClientRect().height` matches `document.body.getBoundingClientRect().height` exactly (assuming `html` has no padding or borders).

### 3. ResizeObserver Semantics & Descendant Resizing

#### Spec Definition & Observed Box
Under the W3C ResizeObserver specification:
- The default observed box is `'content-box'`. Observing an element listens for changes in its `contentBoxSize` or `borderBoxSize`.
- Resizing a descendant element (such as a `<textarea style="resize: vertical">`) alters the height of the descendant, which recalculates the block height of parent elements up the DOM tree to `<body>` and `<html>`.
- As `document.documentElement`'s height changes, `ResizeObserver` fires a callback containing `ResizeObserverEntry` records.

#### Descendant Textarea Drag & Scrollbar Toggle Behaviors
- **Textarea Drag**: When the user drags a `resize: vertical` textarea inside the panel, `documentElement`'s height updates during layout. `ResizeObserver` observing `document.documentElement` fires in all three target engines (Chromium, Gecko, WebKit).
- **Scrollbar Toggles**: If a vertical scrollbar appears or disappears on the document (or iframe), the `inline-size` (content width) of `document.documentElement` changes due to scrollbar gutter reservation. `ResizeObserver` detects this width change and fires a callback.

#### Engine Support & Notification Loop Hazard
- **Engine Support**: Supported in Chromium 64+, Gecko 69+, WebKit 13.1+ (Safari 13.1).
- **ResizeObserver Loop Completed With Undelivered Notifications**:
  - **Spec Cause**: Occurs when a `ResizeObserver` callback triggers a DOM mutation or style change that alters an observed element's layout size *at or above* the depth of the current observation pass within the same frame.
  - **Normative Handling**: The browser logs a warning event (`ErrorEvent` with message `"ResizeObserver loop completed with undelivered notifications"`) or console message. Execution is **not** aborted, and no JavaScript runtime exception is thrown.
  - **Mitigation**: Post message dispatches or parent communication triggered inside a `ResizeObserver` callback should be wrapped in `window.requestAnimationFrame()` or `setTimeout(..., 0)` to decouple parent layout changes from the current observation frame.

### 4. Cross-Document postMessage & VS Code Webview Mechanics

#### HTML Spec postMessage Algorithm
Section 9.4.3 of the HTML Living Standard ("Posting messages") dictates step 6 of `window.postMessage(message, targetOrigin, [transfer])`:

> "6. If the targetOrigin argument is provided and is not a single U+002A ASTERISK character ('*'), and the target document's origin is not same-origin with targetOrigin, then abort these steps silently."

When `targetOrigin` does not match the actual origin of the receiving `window.parent`:
- The browser **silently aborts** dispatching the `MessageEvent`.
- It **does not throw** a `SecurityError` or any JavaScript exception.

#### VS Code Webview Origin Semantics
In VS Code desktop and web implementations:
- Webviews are loaded inside cross-origin `<iframe>` instances with a isolated origin scheme: `vscode-webview://<uuid>` (on desktop) or `https://<uuid>.vscode-cdn.net` (on web).
- Inside the webview panel document, `window.location.origin` evaluates to `vscode-webview://<uuid>` or `https://<uuid>.vscode-cdn.net`.
- The parent window (VS Code workbench) has origin `vscode-file://vscode-app` or `https://vscode-vfs.github.dev`.
- Direct `window.parent.postMessage(msg, targetOrigin)` calls with an explicit HTTPS or HTTP origin mismatch silently drop. In VS Code webviews, communications to the host should use the VS Code API bridge (`acquireVsCodeApi().postMessage(msg)`) or `window.parent.postMessage(msg, '*')` if listening on the workbench frame.

### 5. Cross-Origin Framing Detection & Property Security

#### Window Reference Comparison Table

| Property / Expression | Cross-Origin Behavior | Return Value inside Iframe | Throws SecurityError? |
| :--- | :--- | :--- | :--- |
| `window.parent === window` | Allowed (Cross-Origin Whitelisted) | `false` | **No** |
| `window.top === window` | Allowed (Cross-Origin Whitelisted) | `false` | **No** |
| `window.parent` | Allowed (Cross-Origin Whitelisted) | `WindowProxy` | **No** |
| `window.top` | Allowed (Cross-Origin Whitelisted) | `WindowProxy` | **No** |
| `window.frameElement` | Restricted (Same-Origin Check) | `null` or throws | **Yes** (Throws `DOMException` cross-origin) |

#### Spec Justification
Under HTML Living Standard Section 7.2 ("Cross-origin objects"), `parent`, `top`, `location`, `postMessage`, `window`, `frames`, `self`, and `closed` are explicitly whitelisted on `WindowProxy` for cross-origin access.

- `window.parent === window` is the standard, normative, non-throwing check to determine if a document is top-level.
- Attempting to inspect `window.frameElement` across origin boundaries triggers the cross-origin security check and throws a `SecurityError` `DOMException` in WebKit, Blink, and Gecko.

### 6. Box-Sizing Arithmetic: offsetHeight vs clientHeight

#### Spec Definitions
Under the CSSOM View specification:
- `offsetHeight`: Returns the layout border-box height of the element, including vertical padding, top/bottom borders, and any horizontal scrollbar height. Returned as a rounded integer.
- `clientHeight`: Returns the layout content-box height plus vertical padding, excluding borders and horizontal scrollbars. Returned as a rounded integer.

For an element with `box-sizing: border-box` and `overflow: hidden` (ensuring no horizontal scrollbar gutter exists):
$$\text{offsetHeight} - \text{clientHeight} = \text{Border-Top Width} + \text{Border-Bottom Width}$$

#### Sub-Pixel and Fractional Precision Errors
Because both `offsetHeight` and `clientHeight` round fractional values to integer `layoutInt` types:
- Sub-pixel border widths (such as `0.5px`, `1.5px`, or borders scaled by fractional CSS transforms or device pixel ratio / browser zoom) cause rounding discrepancies.
- For example, two `1.5px` borders total `3.0px`. However, integer rounding on individual layout boxes can yield `offsetHeight = 103` and `clientHeight = 100`, reporting a difference of `3px`, or round to `4px` depending on offset pixel alignment.
- Precision measurement of borders requires `window.getComputedStyle(el).borderTopWidth` combined with `getBoundingClientRect()`.

#### Behavior Under display: none
If an element or any of its ancestors has `display: none`:
- The element does not generate a principal layout box.
- Both `offsetHeight` and `clientHeight` return `0`.
- $\text{offsetHeight} - \text{clientHeight}$ evaluates to `0`.

## Recommended Practices

### 1. Robust Natural Height Measurement Implementation

For a same-origin or webview panel document with `body { margin: 0 }` and `html { height: auto }`, measure natural height using `getBoundingClientRect().height` on `document.documentElement` (or `document.body`).

```javascript
/**
 * Measures the true natural content height of the document.
 * Safe against iframe viewport height stretching.
 */
function getNaturalContentHeight() {
  // Ensure html/body have not been assigned 100% height or flex stretch
  const docEl = document.documentElement;
  const body = document.body;
  
  // Use getBoundingClientRect for sub-pixel accuracy
  const docRect = docEl.getBoundingClientRect();
  const bodyRect = body ? body.getBoundingClientRect() : docRect;
  
  // Choose the larger of root or body border-box, ignoring scrollHeight floor
  return Math.ceil(Math.max(docRect.height, bodyRect.height));
}
```

### 2. Safe Live Observation Pattern

To observe height changes (including user textarea drags and scrollbar toggles) without triggering "ResizeObserver loop completed with undelivered notifications" warnings:

```javascript
let rAfId = null;

function notifyParentOfHeightChange() {
  if (rAfId !== null) return;
  
  rAfId = window.requestAnimationFrame(() => {
    rAfId = null;
    const height = getNaturalContentHeight();
    
    // Check framing safely without throwing cross-origin exceptions
    if (window.parent && window.parent !== window) {
      // Use '*' for cross-origin / webview resiliency, or specific origin for same-origin
      window.parent.postMessage({ type: 'PANEL_RESIZE', height }, '*');
    }
  });
}

const observer = new ResizeObserver(() => {
  notifyParentOfHeightChange();
});

// Observe root document element
observer.observe(document.documentElement);
```

## Opinion and Community Conventions

1. **`document.body.scrollHeight` Usage**: Stack Overflow posts frequently recommend `document.body.scrollHeight` for iframe auto-resizing. While this works in certain legacy quirks-mode scenarios or specific layout setups, it is **unreliable** in standards mode if `body` stretches or if child margins collapse outside `body`.
2. **Third-Party Libraries (`iframe-resizer`)**: Community libraries often compute max combinations of `body.offsetHeight`, `body.scrollHeight`, `documentElement.offsetHeight`, and `documentElement.scrollHeight`. In a tall iframe (700px), taking the `Math.max()` of these values causes permanent "height locking" at 700px because `scrollHeight` includes the viewport floor.

## Candidate API Trade-off Evaluation

| Property / API | Value in 700px Iframe (510px Content) | Handles Content Shrinking? | Affected by Viewport Height? | Recommendation | Failure Mode |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `documentElement.scrollHeight` | `700px` | **No** | **Yes** (Floors at Viewport) | **REJECTED** | Locks iframe to 700px; never resizes smaller. |
| `body.scrollHeight` | `700px` (or `510px` if unstretched) | **Partial** | **Engine Dependent** | **REJECTED** | Floored by root context in some engines; fails on collapsed margins. |
| `documentElement.getBoundingClientRect().height` | `510px` | **Yes** | **No** (When `height: auto`) | **RECOMMENDED** | Returns incorrect height if `html { height: 100% }` is set in CSS. |
| `body.getBoundingClientRect().height` | `510px` | **Yes** | **No** (When `height: auto`) | **RECOMMENDED** | Fails to measure root padding/borders if present; requires `body { margin: 0 }`. |

## Glossary of Terms

- **Scrolling Area**: The total bounding box of all flow content inside a scroll container, including padding and overflow regions.
- **Content Box**: The area bounded by the content edge of an element, excluding padding, borders, and margins.
- **Border Box**: The area bounded by the border edge of an element, including content, padding, and borders.
- **Viewport**: The visible polygonal framing window (Initial Containing Block surface) in which document content is rendered inside an iframe or browser window.
- **Initial Containing Block (ICB)**: The containing block established by the user agent for top-level formatting, matching the dimensions of the viewport for continuous media.
- **Root Element**: The top-most element in the document tree (`<html>` for HTML documents).
