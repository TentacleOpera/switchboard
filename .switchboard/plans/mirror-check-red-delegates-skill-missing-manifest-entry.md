# `mirror:check` is red because the `delegates` skill was never added to MIRROR_MANIFEST — and the fix the error message recommends deletes the skill

## Goal

Add the missing `delegates` entry to `MIRROR_MANIFEST` in `src/services/ClaudeCodeMirrorService.ts` so the generator reproduces the committed `.claude/skills/delegates/SKILL.md`. This clears run-step 11 of the CI workflow — **the first failing step, and therefore the one keeping every step behind it dark** — and, more importantly, closes a live path in which the next extension activation **deletes a working skill** from `.claude/skills/` and silently removes it from Claude Code.

### Problem Analysis

`npm run mirror:check` (`scripts/check-claude-mirror.js`) fails at HEAD:

```
❌ mirror:check — .claude/skills drift detected. Run the extension activation (or `generateClaudeMirror` on the repo root) and commit the regenerated mirror.
  Missing from regenerated (committed only):
    - delegates/SKILL.md
```

The check regenerates the mirror from the committed `.agents/` source into a temp directory using the same `generateClaudeMirror` the extension uses, then diffs it against the committed `.claude/skills/`. It is reporting, correctly, that a file is committed which the generator does not produce.

**The state, verified at HEAD:**

| Artefact | Contains `delegates`? |
| :--- | :--- |
| `.agents/skills/delegates/SKILL.md` | present, committed, clean — **no frontmatter** |
| `.claude/skills/delegates/SKILL.md` | present, committed, clean — with correct generated frontmatter |
| `.agents/.switchboard-bundled.json` (control-plane bundle ledger) | yes — `"skills/delegates/SKILL.md"` (line 35) |
| `.claude/.switchboard-generated.json` (mirror prune ledger, **committed**) | yes — 48 skills, including `{source: "skills/delegates", name: "delegates"}` |
| `MIRROR_MANIFEST` in `src/services/ClaudeCodeMirrorService.ts` | **no** — 47 entries (lines 47–259), string `delegates` absent from the entire file |
| `git log -S"delegates" -- src/services/ClaudeCodeMirrorService.ts` | **no commits** — it was never in the manifest, in any revision |
| compiled `out/services/ClaudeCodeMirrorService.js` | **no** |
| the **installed** VSIX `turnzero.switchboard-1.7.13` — `dist/extension.js` | **no** — 0 occurrences of `skills/delegates` |
| the **installed** VSIX — bundled `.agents/skills/delegates/SKILL.md` | present |

`delegates` is the **only** orphan. Cross-checking the 47 manifest `name:` values against the 48 directories under `.claude/skills/` yields exactly one committed-but-not-generated name (`delegates`) and zero manifest-but-not-committed names. There is no second instance of this hiding behind the first.

The skill was added in `1bd39f4a` ("terminals fleet, tickets subtasks, standalone pty, delegate contract"), the most recent `src/`-touching commit and currently **unpushed**. That commit landed the `.agents/` source, the `.claude/` mirror, and the ledger entry — but not the manifest entry that makes the generator emit any of it.

> **Superseded:** "How the committed mirror came to exist is undetermined… it was either generated by an extension build whose manifest carried the entry (the installed VSIX is a different build lineage from `src/`), or hand-authored to match the generator's output byte-for-byte. Both are consistent with the evidence."
> **Reason:** The first branch was checkable and is now falsified. The installed VSIX (`~/.devin/extensions/turnzero.switchboard-1.7.13/dist/extension.js`) contains **zero** occurrences of `skills/delegates`; `out/` and `dist/` in this repo contain zero; and `git log -S` finds it in no revision of the source. **No build that exists anywhere on this machine produces that mirror file.** It and its ledger row were authored by hand (or by a build that no longer exists).
> **Replaced with:** The provenance is resolved and it changes one thing that matters — see "The severity" below. The entry is missing from `src/` either way; that is still what must be added, and the fix does not depend on this. Do not spend further time on provenance.

**A second discovery path exists and does not help.** `generateClaudeMirror` has a dynamic scan after the manifest loop (lines 469–501), but it only matches loose files: `file.startsWith('switchboard-') && file.endsWith('.md')` directly under `.agents/skills/`. `delegates` is a *directory* (`skills/delegates/SKILL.md`), so the scan never sees it. The manifest is the only route.

### Root Cause

The skill-discovery mechanism is host-split. Antigravity reads `.agents/skills/` from the filesystem, so dropping a directory there is sufficient and the skill works immediately. Claude Code reads `.claude/skills/`, which is **generated** from `MIRROR_MANIFEST`. Adding a skill therefore requires two edits in lockstep — the source directory *and* the manifest entry — and only the first is self-evidently necessary, because the skill appears to work the moment it exists. `1bd39f4a` made the first and not the second.

### The severity: this is not a drift tick, it is a pending deletion — **armed on the currently installed extension**

`generateClaudeMirror` prunes. It deletes any skill the ledger says it previously wrote that was **not regenerated this run** — the mechanism that stops retired commands staying user-invokable forever on existing installs:

```ts
const ledgerPath = path.join(claudeDir, GENERATED_MANIFEST_FILE);   // .claude/.switchboard-generated.json
if (fs.existsSync(ledgerPath)) {
    const previous = JSON.parse(fs.readFileSync(ledgerPath, 'utf8'));
    const regenerated = new Set(generatedSkills.map(s => s.name));   // 47 names — no 'delegates'
    const prevSkills = Array.isArray(previous?.skills) ? previous.skills : [];
    for (const prev of prevSkills) {                                 // 48 names — includes 'delegates'
        if (!prev?.name || regenerated.has(prev.name)) continue;
        const staleDir = path.join(skillsRoot, prev.name);
        if (!staleDir.startsWith(skillsRoot + path.sep)) continue;
        fs.rmSync(path.join(staleDir, 'SKILL.md'), { force: true });  // ← deletes the mirror
        try { fs.rmdirSync(staleDir); } catch { /* non-empty — leave the dir */ }
    }
}
```

The ledger lists 48 skills. A build from HEAD's `src/` regenerates 47. `delegates` is in the ledger and not in `regenerated`, so on the next activation its `SKILL.md` is deleted and its directory removed. The ledger is then rewritten with the 47 that were regenerated, so the skill is simply gone — no second chance, no diagnostic. The `delegates` skill disappears from Claude Code.

**This is demonstrated, not inferred.** Copying `.agents/` **and** `.claude/` into a temp root and running the compiled generator there reproduces it exactly:

```
before: delegates present? YES  ledger=48
result: {"status":"generated","reason":"Mirrored 47 skill(s) into .claude/skills/","skillsWritten":47}
after:  delegates present? NO   ledger=47
dir still there? NO (rmdir succeeded)
```

**And the deletion is armed on the extension that is installed right now**, not deferred to some future release build. `scaffoldProtocolLayers` (`src/extension.ts:3909-3923`) calls `generateClaudeMirror(workspaceUri.fsPath, version)` whenever the workspace's protocol targets include `claude` — which this repo's do, since it carries a `CLAUDE.md`. The installed 1.7.13 bundle has no `delegates` manifest entry (verified above), so the next time that extension activates on this workspace it performs the prune shown above.

The prune ledger is **committed**, so this is not one developer's local hazard; it travels with the repo.

### The trap: the error message's own remedy performs the deletion

> *"Run the extension activation (or `generateClaudeMirror` on the repo root) and commit the regenerated mirror."*

Follow that literally at HEAD and the generator prunes `.claude/skills/delegates/`, rewrites the ledger to 47, and `mirror:check` goes **green** — because the committed mirror now matches a generator that produces nothing for `delegates`. A working skill is deleted, the check passes, and CI advances. **The failure looks exactly like the fix.** The remedy text is correct for the ordinary drift case it was written for (a stale mirror committed against a current manifest) and is precisely wrong for this one: here the mirror is *ahead* of the manifest, and the manifest is what is missing.

The trap has a second stage on a normal developer machine. Activation prunes the file, so `git status` shows a *deleted* `.claude/skills/delegates/SKILL.md` plus a modified ledger. Committing that — the natural "commit the regenerated mirror" reflex — makes the deletion permanent for everyone on the repo *and* turns CI green. `git checkout .` restores it and re-arms the same trap for the next activation.

This is also the mechanism `mirror:check` exists to backstop — its own header names it: *"the exact failure mode behind the 'skill fixes don't stick' bug this guard backstops."* The guard is working. The remedy is what needs judgment.

## Complexity Audit

### Routine

- One entry appended to one array in one file. No schema, no migration, no runtime path, no network surface.
- The entry's exact shape is **recoverable from the committed mirror's own frontmatter** — it is not a judgment call. See Proposed Changes.
- The proposed entry has been **pre-verified byte-identical** by simulating `parseSource` + `buildSkillMd` over it (sha256 `ac7488a9…` both sides). The usual "did I get the string right?" risk is already retired before a line is written.
- `mirror:check` already exists, is already wired into CI at run-step 11, and already has a `package.json` script. No new wiring.
- Self-healing on installs: any install that has already pruned `delegates` regenerates it on the next activation once the manifest entry exists. No migration or repair script needed.

### Complex / Risky

- **The obvious remedy is destructive and produces a green check.** The failing tool prints instructions that, followed at HEAD, delete a working skill and make the check pass. Nothing downstream distinguishes that outcome from a correct fix. This is the entire risk of this plan and the reason it is not an Intern task.
- **`descriptionFallback` must be byte-identical to the committed mirror's description.** `.agents/skills/delegates/SKILL.md` has **no frontmatter**, so `parseSource()` yields no description and `buildSkillMd()` falls through to `entry.descriptionFallback`. Any difference — a changed dash, a dropped clause, curly vs straight quotes — leaves `mirror:check` red with a confusingly *modified*-rather-than-missing diff. The literal in Proposed Changes is verified correct; copy it, do not retype it.
- **Do not regenerate against the committed tree.** Regeneration at HEAD deletes the file whose frontmatter is the specification for the entry being written, and mutates the committed ledger. Add the entry first; verify in a temp root, never on the repo root. See Verification Plan.

## Edge-Case & Dependency Audit

- **Race conditions.** None. Generation is synchronous and runs at activation.

- **Security.** None directly. The prune loop's path-traversal guard (`staleDir.startsWith(skillsRoot + path.sep)`) is correct and untouched. `allowedTools: 'Bash'` on the new entry grants the skill the same tool access the committed mirror already declares — it is not a widening.

- **Side effects.** Adding the entry changes what the next activation writes: `.claude/skills/delegates/SKILL.md` becomes generator-owned (it is currently an orphan the generator neither writes nor prunes-by-name... until the ledger mismatch prunes it). The ledger regenerates from 47 back to 48. Both are the intended outcome.

- **The regenerated file must be byte-identical to the committed one.** If it is not, the entry is wrong — most likely the `descriptionFallback`, `allowedTools`, or `invocation`. Treat any diff in `.claude/skills/delegates/SKILL.md` after regeneration as a failed fix, not as "the generator's preferred formatting". `mirror:check` asserts exactly this: it sha256-compares every regenerated file against its committed counterpart, so a green check *is* the byte-identity proof.

- **`invocation` must be `'no-user'`, not `'no-model'`.** The mapping in `buildSkillMd()` (lines 420–425) is explicit: `'no-model'` emits `disable-model-invocation: true`; `'no-user'` emits `user-invokable: false`. The committed mirror carries `user-invokable: false`, so the entry is `'no-user'` — model-loadable, hidden from slash. Confirmed by simulation: the `'no-model'` variant does **not** reproduce the committed file. That matches the skill's nature: a child-side contract a delegate agent loads, never something a human types. It also matches the treatment of the nearest analogues in the manifest (`switchboard-contracts`, `tuning`).

- **The description needs no escaping in a single-quoted TS literal.** It is 355 characters with exactly **one** non-ASCII codepoint — `U+2014 EM DASH` at index 29 — and contains **no apostrophe**, unlike neighbouring entries (`improve-feature`, `design-system-builder`) which carry `\'`. Paste it between plain single quotes as-is.

  > **Superseded:** "it contains an em dash and a non-breaking-looking space run that are easy to corrupt by hand."
  > **Reason:** Checked character by character — there is no unusual whitespace anywhere in the string. Warning about a hazard that does not exist sends the implementer hunting for a phantom and implies the literal is more fragile than it is.
  > **Replaced with:** One non-ASCII character (the em dash), no apostrophes, no exotic whitespace. Copy-paste is safe; hand-retyping is what breaks it, because of the em dash alone.

- **Installs that already pruned the skill.** Harmless and self-correcting: with the entry present, the next activation writes the file back and re-adds it to the ledger. No user data is involved — `.claude/skills/` is generated content, not authored state — so no migration applies.

- **The other 47 entries must be untouched.** A reflexive "regenerate everything" pass could reformat or reorder unrelated mirror files. The final diff must be exactly one file: `src/services/ClaudeCodeMirrorService.ts`.

- **Dependencies & conflicts.** `.claude/`, `CLAUDE.md`, and `AGENTS.md` are shared surfaces — this change is a single append to a manifest array and must not touch anything else in them. No other gate reads the mirror (`parity:check`, `push-routing:check`, `verb-returns:check` are all green at HEAD and unrelated).

- **`mirror:check` requires a compiled `out/`.** The script loads `out/services/ClaudeCodeMirrorService.js` and exits 1 with an explicit message if it is absent. CI satisfies this — `npm run compile-tests` is run at run-step 3, well ahead of `mirror:check` at run-step 11 — so CI's red result is valid, not an environment artefact.

- **The workflow file has uncommitted additions; the run-step numbering above is still correct for `mirror:check`.** `.github/workflows/integration-tests.yml` carries 4 unstaged new run steps (`unattended-batch`, `kanban-view-plan-removal`, `dispatch-view`, `terminal-plan-attribution`). All four are inserted at file lines 86, 288, 297 and ~609 — i.e. **after** `mirror:check` at line 53 — so `mirror:check` remains run-step 11. The downstream failing steps cited under Dependencies shift by up to +4 once those additions are committed; do not treat those numbers as stable identifiers.

## Adversarial Synthesis

**Risk Summary.** The dominant risk is that the fix is the destructive path: the failing check prints "regenerate and commit the mirror", and doing that at HEAD prunes a working skill, rewrites the ledger without it, and turns the check green — a deletion that is indistinguishable from a repair at every automated gate, and one the currently installed extension performs on its next activation without being asked. The second risk is a near-miss entry: because `.agents/skills/delegates/SKILL.md` carries no frontmatter, the manifest's `descriptionFallback` is the sole source of the mirror's `description:` line — mitigated here by pre-verifying the exact literal against the committed file (sha256 match). The third is ordering: any regeneration must happen in a temp root, never on the repo root, or it destroys the file whose frontmatter specifies the entry and dirties the committed ledger.

## Proposed Changes

### `src/services/ClaudeCodeMirrorService.ts` — add the missing `delegates` manifest entry

**Context.** `MIRROR_MANIFEST` (declared at line 47, closing at line 259) currently holds 47 entries. Place the new entry alongside the other agent-facing, non-slash contract skills — immediately after the `switchboard-contracts` entry (lines 227–231, the last entry before the `switchboard-*` alias block) is the natural home, since both are behaviour contracts a model loads rather than doors a user types.

**Logic.** The entry's every field is determined by the committed mirror it must reproduce:

| Field | Value | Determined by |
| :--- | :--- | :--- |
| `source` | `'skills/delegates'` | the committed ledger's `"source": "skills/delegates"`, and the on-disk directory |
| `name` | `'delegates'` | the mirror's `name: delegates` and its directory name |
| `invocation` | `'no-user'` | the mirror's `user-invokable: false` (`buildSkillMd` maps `'no-user'` → that line) |
| `allowedTools` | `'Bash'` | the mirror's `allowed-tools: Bash` |
| `descriptionFallback` | the exact string below | the mirror's `description:` — the source has no frontmatter, so the fallback is the only producer |

**Pre-verified.** These five fields were run through the generator's own logic (`parseSource` over `.agents/skills/delegates/SKILL.md`, then `buildSkillMd`) and reproduce `.claude/skills/delegates/SKILL.md` **byte for byte**:

```

committed sha256: ac7488a9d5be6513aa53f287a062100f1d110f10e097284bf9a9a49d8a2d2ab7
BYTE-IDENTICAL: true          (no-model variant: false)
```

**Implementation.**

```ts

    // the prune loop removes any ledger-tracked name that was not regenerated — so the

    {
```

Copy the `descriptionFallback` from `.claude/skills/delegates/SKILL.md` line 3 (strip its surrounding double quotes) rather than retyping it — the em dash at character 29 is the one thing hand-typing gets wrong.

**Edge cases.** Do **not** "fix" the source by adding frontmatter to it. Two things break. First, `parseSource()` would win over `descriptionFallback` and the two would have to agree or the mirror changes. Second — and the real reason — the absence of frontmatter is deliberate: it is how a skill stays out of Antigravity's filesystem discovery while remaining reachable via the AGENTS.md skills table and by path. 36 of the 39 skill directories are frontmatter-less for exactly this reason, and `delegates` is a child-side contract an agent loads, never a door a human types. Leave the source alone; the fallback is what makes the entry correct.

## Verification Plan

The session running this work carries **SKIP COMPILATION** and **SKIP TESTS** directives, so the plan is split into a compile-free tier the implementer runs locally and a gate tier CI runs. The compile-free tier is not a weaker substitute — it exercises the generator's own logic directly and is decisive on its own.

### Compile-free verification (run these)

1. **Inspection against the committed mirror.** Open `.claude/skills/delegates/SKILL.md` and confirm the new entry's four literal fields match its frontmatter one-for-one: `name: delegates` → `name: 'delegates'`; `allowed-tools: Bash` → `allowedTools: 'Bash'`; `user-invokable: false` → `invocation: 'no-user'` (**not** `'no-model'` — that emits `disable-model-invocation: true` and is a different file); `description: "…"` → `descriptionFallback: '…'` with the quotes stripped and nothing else changed.

2. **Byte-identity simulation — the decisive check.** Run the generator's own `parseSource`/`buildSkillMd` logic over the source with the new entry and hash the result against the committed mirror. It must print `BYTE-IDENTICAL: true` and sha256 `ac7488a9d5be6513aa53f287a062100f1d110f10e097284bf9a9a49d8a2d2ab7`. This is what `mirror:check` will assert in CI, computed without compiling anything.

3. **Negative control — the check must still be able to fail.** Re-run the same simulation with `invocation: 'no-model'` (or with the `descriptionFallback` line removed) and confirm it reports **not** identical. A verification that passes for a wrong entry is verifying nothing. Restore the correct values.

4. **Prune-path simulation — the direct test of the deletion.** Copy `.agents/` **and** `.claude/` into a scratch directory and run `generateClaudeMirror(<scratchRoot>, '1.7.13')` there. Before the fix this prints `Mirrored 47 skill(s)`, deletes `<scratch>/.claude/skills/delegates/SKILL.md`, removes its directory, and leaves a 47-entry ledger. After the fix it must print `Mirrored 48 skill(s)`, leave the file in place, and leave a 48-entry ledger containing `delegates`. **Do this in a scratch copy, never on the repo root** — a root run deletes the specification file and dirties the committed ledger. (This step needs a compiled `out/`; if the session cannot compile, it is the one item to hand to CI along with the gate tier.)

5. **Diff hygiene.** `git diff --name-only` must list `src/services/ClaudeCodeMirrorService.ts` and **nothing else** — no `.claude/skills/**`, no ledger. The committed mirror is already correct; the fix makes the generator agree with it, it does not change it.

> **Superseded:** Original steps 3, 4 and 6 — "Run the regeneration the check describes, then confirm `git diff --stat .claude/skills/delegates/SKILL.md` reports no change… After regenerating, confirm `.claude/.switchboard-generated.json` lists 48 skills… Confirm `git diff --name-only` lists `src/services/ClaudeCodeMirrorService.ts` and nothing else — no `.claude/skills/**` changes, no ledger change."
> **Reason:** Three problems. (a) Steps 4 and 6 contradict each other: the ledger carries `generatedAt: new Date().toISOString()` and `version` (lines 529–541), so **every** root regeneration produces a ledger diff — step 6 can never pass after step 4 runs. (b) Step 3 instructs a regeneration against the committed tree, which is the exact destructive act the plan spends three sections warning against; before the entry exists it deletes the specification file. (c) Step 3's assertion is already what `mirror:check` computes — it sha256-compares generated vs committed for every file — so it added a hazardous manual step to re-derive a result the gate already gives.
> **Replaced with:** Steps 1–5 above. All regeneration happens in a scratch copy; byte-identity is asserted by simulation (and again by `mirror:check` in CI); the ledger assertion moves into the scratch run where a changing timestamp is irrelevant; and diff hygiene becomes achievable because the repo tree is never regenerated into.

### Manual

9. In a Claude Code session on this repo, confirm `delegates` still appears in the available-skills list and is **not** offered as a `/delegates` slash command — `user-invokable: false` means model-loadable only. ## Agent Recommendation

**Send to Coder** (complexity 4) — a one-entry append whose exact text is already verified, but the failing tool prints a remedy that deletes a working skill and turns the check green, so the task is entirely about not doing the obvious thing. An implementer who regenerates against the committed tree, or who retypes the description, produces a passing check and a worse repo.

The reviewer should check three things: that `git diff` contains **only** `src/services/ClaudeCodeMirrorService.ts`; that the byte-identity simulation reports sha256 `ac7488a9…` and the scratch-root regeneration leaves a 48-entry ledger with `delegates` intact; and that `invocation` is `'no-user'` and not `'no-model'` — the two produce different frontmatter and only one matches the committed mirror.

**Recommended follow-up (not in scope here).** This is the seventh instance in one sweep of a contract or generator failing on a legitimate edit, and the second where the failure text pointed at innocent code.

> **Superseded:** "Two durable guards are worth considering as their own plan: a check that every `.claude/skills/*/SKILL.md` has a `MIRROR_MANIFEST` entry (which would have caught this at `1bd39f4a` instead of a week later), and making the prune loop *warn loudly* about a ledger name with no manifest entry rather than silently deleting it."
> **Reason:** The first guard already exists and already fired — `mirror:check`'s "Missing from regenerated (committed only)" branch **is** that check, and it caught this at `1bd39f4a`. Proposing to build it again would spend a plan re-implementing a working gate.
> **Replaced with:** Two guards that genuinely do not exist. **(a) Split the remedy text by branch.** `scripts/check-claude-mirror.js:145` prints one remedy for all three failure modes, but "Missing from regenerated" and "Content drift" have **opposite** fixes — the former means the manifest is behind and regenerating destroys the evidence; the latter means the mirror is behind and regenerating is correct. The `missing` branch should print "a committed mirror has no `MIRROR_MANIFEST` entry — add the entry; do NOT regenerate, it will delete the file." **(b) Make the prune loop refuse-and-warn on an unexplained name.** A ledger entry whose name has no manifest entry *and* whose `.agents/` source still exists is a lockstep-edit miss, not a retirement; the loop should log it and skip the delete rather than silently removing a live skill. The two are cheap and independently useful — (a) is a string change, (b) is a source-exists guard inside the existing loop.
