# Multi-Agent Planning 01 — Fan-In Dispatch: N Agents, One Problem, N Independent Plans

## Goal

Add a planning run mode that dispatches N agents at a *single* problem from different investigative entry points, each producing a complete, independent plan into an isolated run directory, with each investigator's *findings* kept out of every sibling's reach for the duration.

**A planning run is a team.** This plan is written on top of the teams feature (`terminals.agentGroups` + `teamWiring.ts` + `spawnDelegates`), not beside it: the roster is a **team definition**, the investigators are its **members**, the assembling lead is its **head**, and seat provisioning, cap enforcement, standing-order wiring, group registration, pane layout and teardown are all inherited rather than rebuilt. What this plan adds is the **per-run, per-seat** half of the brief — plus the run directory, the brief hygiene guard and the completion condition. If a step below looks like it duplicates something teams already does, it is a bug in this plan.

> **Superseded:** "What this plan adds is the one thing teams does not have — **one brief delivered to every seat**."
> **Reason:** Verified false against the tree on 2026-08-16. Teams *does* have a one-text-to-N-seats carrier: a team definition's `prompt` field is delivered to every member as a single `team`-scoped standing order (`wireSpawnedTeam`, `teamWiring.ts:626-628`; installed at `:681-690`; selected for delivery by `selectOrders`, `standingOrders.ts:104-111`, which excludes the head). What teams genuinely lacks is (a) a way to make that text *vary per seat* — the team prompt is byte-identical for every member — and (b) a way to *start N turns* with it, since `applyStandingOrders` (`standingOrders.ts:147`) decorates an existing message and returns early on empty input, so a standing order needs a dispatch to ride on.
> **Replaced with:** The brief is **split across two carriers**. Its run-invariant half (section schema, cite-`file:line` rule, sibling-isolation rule, report-to-head callback) belongs in the team `prompt`, where it costs zero new code and — because it rides *every* message, not just the first — holds for the whole run rather than only the opening turn. Its per-run and per-seat half (symptom, scope, entry point, output path) must go through an N-way `ptySendPrompt` dispatch, which is the one genuinely new mechanism. See Implementation 2 and 5, and the two traps in Complex / Risky that this split introduces.

This plan owns dispatch and artifact isolation only. Comparing the resulting plans is `multi-agent-planning-02-divergence-map.md`; resolving their disagreements is `multi-agent-planning-03-adjudication-round.md`. Shipping this plan alone is already useful: it produces N plans in a run directory that a human can diff by hand.

### Problem analysis and root cause

**The problem being solved is anchoring in single-agent planning.** One planner explores a codebase, forms a root-cause hypothesis early, and spends the rest of its budget elaborating that hypothesis rather than challenging it. The output is a plan that reads as complete and rests on a false premise. The cost lands downstream — a coding cycle, a review pass, rework, and sometimes a bad merge — which makes planning the highest-leverage place in the pipeline to spend redundant compute.

This repository is unusually hostile to obvious readings, and its own `CLAUDE.md` is the evidence: the plan importer is resolve-only rather than auto-creating projects; `window.confirm()` is a silent no-op in VS Code webviews; `dist/` is not used during development. Each of those is a trap where the natural assumption is wrong. A single planner that anchors on the natural assumption emits a confidently wrong plan. N *independent* planners will tend to diverge at exactly those points, and the divergence is the alarm.

Independent sampling is what buys this: N agents that never see each other's work produce **uncorrelated** errors. Agreement then constitutes evidence, and disagreement localizes the real uncertainty. Coordination during generation destroys that property — agents who read each other's findings anchor collectively, and four agents in confident agreement about a fiction is the worst available outcome because it looks like success.

**Root cause of why this cannot be done today — two hard blockers and one that has since dissolved, all re-verified against the tree on 2026-08-16:**

1. **No 1-brief : N-agent *dispatch* shape exists — and the existing primitive is the opposite transpose.** `switchboard.triggerBatchAgentFromKanban` is the batch primitive (registered `extension.ts:1714`, standalone twin `bootstrap.ts:856`), and it resolves to `TaskViewerProvider.handleKanbanBatchTrigger` (`:6233`), which partitions the plan list by feature and calls `generateUnifiedPrompt(role, group.plans, …)` — **one prompt covering many plans, delivered to one terminal**. The Distribute path (`KanbanProvider.ts:6011-6030`) buckets plans across K terminals and dispatches the buckets concurrently, but no plan is ever sent to two agents; its own comment states "handleKanbanBatchTrigger generates a single prompt per bucket" (`:6015`). So the shipped mapping is **M plans : 1 agent** (and M plans : K agents), already a fan-in on the *plan* axis. What this plan needs is the transpose on the *agent* axis — one dispatch fanned to N seats — and no call path produces it. There are 12 `triggerBatchAgentFromKanban` call sites in `KanbanProvider.ts` (5953, 6025, 7564, 7611, 8952, 9688, 9761, 9832, 9903, 10683, 10765, 10842); `:5953` is the `planner` / `improve-plan` one. Every one of them passes a *list of plans* and, at most, a single target terminal.

   **Two adjacent primitives that are near-misses, and why neither closes the gap.** Name them explicitly so a coder does not rediscover them and assume the work is already done:
   - **`team.prompt`** delivers one *text* to N seats (see the Superseded callout above) but cannot vary per seat and does not start a turn. It carries the invariant half of the brief; it cannot carry the entry point or the output path.
   - **`ptyCreateBatch`** (`bootstrap.ts:1298`, `ptyHost.ts:115`, `ptyFleetService.createBatch`) creates a *hidden fleet* of N terminals over HTTP in one call — deliberately agent-only, with no webview call site (`src/test/pty-route-surface-contract.test.js:26-38`). It is a fan-out on the **seat-creation** axis, not the **prompt** axis: it allocates terminals and returns handles, and delivers no prompt at all. It is a genuine alternative to team auto-start for *provisioning* (see the Architecture note under Proposed Changes), but it is not the missing dispatch.

2. **Draft plans cannot be written to `.switchboard/plans/`.** That directory is watched and auto-imported: `TaskViewerProvider._reconcileOnDiskLocalPlanFiles` (`:15657`) enumerates it via `_listSupportedLocalPlanPaths` (`:15734`), and watchers are registered at `:13867` (`createFileSystemWatcher`) with a native `fs.watch` fallback at `:13940`. Nesting does not escape it: the enumerator recurses exactly one level into subdirectories (the multi-repo layout — re-read `:15734-15775`, the `entry.isDirectory()` branch), and the watcher glob is recursive — so `.switchboard/plans/<run-id>/` would import just as readily as the flat directory. Writing N drafts per run into it would import N junk cards onto the board every run, and the user would have to delete them by hand. Run artifacts must therefore live outside the watched tree.

3. **Cross-agent comms suppression is *not a blocker at all* — the teams topology already provides it.** This was written as a blocker before the teams feature landed, and teams answers it structurally rather than by suppression. Every relationship preset in `src/services/linkPresets.ts` carries a `direction` of either `head-receives` or `member-receives` (`:59-119`) — **there is no peer-to-peer preset, and no way to express one**. A member cannot be told about another member; it can only be told about the head. So the standing-orders channel is incapable of carrying one investigator's findings to another, and the "turn comms off for phase 1" requirement dissolves.

   The vector that survives is the **filesystem**, not the message channel. An investigator handed a path to the run *directory* rather than to its own output file can read every sibling draft, and nothing in teams prevents that. Scoping each seat's output path is therefore the whole of the independence mechanism — see Implementation 6.

   **Do NOT pass `standingOrders: false` on phase-1 dispatches.** The opt-out exists (`ptySendPrompt` reads `payload.standingOrders !== false` — `bootstrap.ts:1453` and `:1667`, extension side `TaskViewerProvider.ts:425`; the Link-up modal uses it at `terminals.js:8879`) and using it here would be actively harmful: the `reports-to-head` instruction is what makes each investigator report to the head on completion, and suppressing the standing-orders block deletes the run's completion signal to prevent a leak the topology already makes impossible.

There is no standing-order budget to plan around.

**What is genuinely left to build**, and nothing more: (a) the per-run / per-seat dispatch that starts N turns with a varying brief tail (blocker 1); (b) the run directory with a per-seat output path (blocker 2); (c) the brief hygiene guard, which must cover **both** brief carriers; (d) the run completion condition on top of the callbacks teams delivers.

**Three teams constraints that shape the design:**

- **One team per head role.** `migrateAgentGroups` step 3 (`teamWiring.ts:236-273`) marks a second team claiming an already-taken `headRole` as `unassigned: true`, and an unassigned team is visible and editable but **does not auto-start** (`findTeamForHeadRole` skips it, `:426`). A planning team must therefore claim a head role no other team holds — if the operator already has a team on `lead`, the planning team needs its own head role or it will silently never spawn.
- **Member `scope` decides survival.** `per-team` (the default applied by `migrateAgentGroups` step 2) means parented to the head: counted against both delegate caps and torn down when the head is killed. `shared` means unparented, reused across teams by the name `${teamName}-${label||role}`, outside `liveDelegateCount()` and outside head-owned teardown (`ptyFleetService.ts:439-447`, `:471`). Investigators should be `per-team` — they are run-scoped and should die with the run. This matters again in plan 03, where the adjudicator wants the opposite.
- **The per-head cap pre-flight counts `shared` members; `spawnDelegates` does not.** `spawnDelegates` filters them out (`ptyFleetService.ts:457`, `.filter(d => d.scope !== 'shared')`) but `instantiateAgentGroupCore` sums **every** member (`agentGroupInstantiation.ts:77-79`) despite a comment at `:73` claiming to "Mirror spawnDelegates' own arithmetic exactly". The two disagree. Consequence for the roster: **investigators + any `shared` member must total ≤ 8**, even though only the investigators are truly parented. At the recommended 3–5 investigators this is slack, but it is the ceiling to size against — and it is the constraint plan 03's `shared` adjudicator seat runs into.

### Contract and blast-radius notes

**A contract correction that affects implementation.** `switchboard-contracts` #2 defines completion as the first plan-file `mtime` advance after `dispatched_at` is set, and #3 makes plan files write-once-at-the-end for dispatched coders. Both govern *a dispatched card's own plan file*. Phase-1 investigators are writing **new** files into a run directory and are not dispatched cards in that sense, so neither contract detects their completion. Run completion needs its own mechanism — which teams half-supplies via the `reports-to-head` callback (contract #9: a message delivered to an idle terminal *is* the turn), though the callback is agent-authored text and so cannot be the authority. See Implementation 8.

**Blast radius.** Additive. No existing dispatch path changes shape; the plan watcher is untouched; the board gains nothing until plan 02 emits a synthesized plan into `.switchboard/plans/`. One shared-state caveat: a planning team occupies a head role and consumes the delegate budget alongside any live coding team — see Dependencies & Conflicts.

## User Review Required

Three decisions the user should make before this is coded, because all three are cheap to set now and annoying to change later:

1. **Fleet size and entry points.** The design assumes four: failing behavior / tests and contracts / git history / architecture. Fewer than three loses the divergence signal; more than about five is mostly duplicated exploration. As a team this is member `count`, and the ceiling is set for you: `MAX_DELEGATES_PER_PARENT = 8` per head (`src/standalone/ptyFleetService.ts:10`), so any roster in the 3–5 range fits without touching the caps. Note the pre-flight quirk above — if plan 03's `shared` adjudicator is added to the same team definition, it counts against that 8 even though `spawnDelegates` exempts it.
2. **Which head role the planning team claims.** One team per head role is enforced, and a colliding team lands `unassigned` and never auto-starts. If the operator's existing team already heads `lead`, the planning team needs a distinct head role. Recommend a dedicated one rather than sharing `lead`, so a planning run and a coding team can coexist.
3. **Whether the brief is human-reviewed before dispatch.** The brief is the single point of failure — N agents working from a bad brief produce N bad plans. Recommend a review gate for the first several runs, then make it optional. Note this now covers **both** carriers: the per-run dispatch text *and* the team `prompt`, which is written once and thereafter invisible.

## Complexity Audit

### Routine

- Creating a run directory and writing per-agent output paths into it.
- Assigning an entry point per seat from a static list at dispatch time.
- Reusing the existing PTY dispatch path to deliver a prompt to an idle terminal.
- Provisioning the seats: a team definition plus the existing auto-start trigger. No spawner, no cap arithmetic, no group registration, no layout choice, no teardown — teams owns all of it.
- Carrying the run-invariant half of the brief as the team definition's `prompt` — a data field, not a code path.

### Complex / Risky

- **The brief must not contain the lead's diagnosis — in *either* carrier.** The natural instinct when composing a brief is to share what is already suspected, and one such sentence anchors every investigator, destroying the independence the run exists to buy. The brief carries symptom, scope, required sections and the entry-point assignment — never a root cause. This is the single most important behavioural constraint in the plan and it is a prompt-authoring discipline, not a code path, so it needs an explicit guard (see Implementation 7). **A guard that checks only `brief.md` has a hole**: the team `prompt` reaches every investigator on every message and would sail past it. Guard both, or the guard is theatre.
- **A per-run brief must NOT live in `team.prompt` — the team order is written once and never updated.** `wireSpawnedTeam` installs the team-scoped order behind an existence check keyed on `(scope, teamId)` — `const teamExists = next.some(o => o.scope === 'team' && o.teamId === groupId); if (!teamExists) { next.push(...) }` (`teamWiring.ts:681-690`) — and `groupId` is derived deterministically from the head name (`:619-620`). Idempotency is deliberate and correct for invariant prose, but it means **run 2's investigators would silently receive run 1's brief**. Only genuinely run-invariant text (section schema, cite rule, sibling isolation, callback) may live there. Everything run-specific goes through the dispatch, or the run directory must explicitly rewrite the team-scoped order before each run — which is extra code that the split avoids.
- **Overriding `team.prompt` REPLACES the defaults, it does not merge with them.** `teamWiring.ts:626-628` reads `prompt ? prompt.replace(...) : \`${AGENT_GROUP_CALLBACK_INSTRUCTION}\n${GIT_SAFETY_DIRECTIVE}\``. Supplying a custom team prompt that omits the `reports-to-head` callback therefore **deletes the run's completion signal** — the same failure the `standingOrders: false` warning below exists to prevent, reached through a second door the operator is far more likely to walk through, since writing a team prompt feels like adding text rather than removing it. It also drops `GIT_SAFETY_DIRECTIVE` (`agentPromptBuilder.ts:558`). Any custom team prompt MUST re-include both, verbatim.
- **Independence is a filesystem property here, not a messaging one.** "Do not read the other agents' output" as advisory prose will be violated eventually, and a violation is invisible in the output — a plan that quietly incorporated a neighbour's finding looks identical to one that didn't. The teams topology already closes the messaging vector (no peer-to-peer preset exists), so the entire remaining risk is path scoping: give each investigator a path only to *its own* output file, and never hand a seat the run directory itself.
- **Everything in `team.prompt` is a *shared* input, and shared inputs are a correlated-error vector.** The value of the run rests on uncorrelated errors. Any framing, terminology or worked example placed in the team prompt is read identically by all N seats and will push them toward the same reading. Keep the team prompt to mechanical discipline (output schema, citation rule, isolation rule, callback) and keep interpretation out of it. Plan 02 must be told what was in the team prompt, so it does not score a shared-input artefact as independent agreement.
- **Run completion detection is a *reconciliation*, not a new signal.** Teams already delivers one: the `reports-to-head` instruction, carried in the team prompt, tells each member to POST its report to the head when it finishes, and per `switchboard-contracts` #9 that message starts a turn on the head. So the head wakes N times, once per investigator, for free. But the callback is **agent-authored text** — the class of signal contract #2 deliberately refuses to trust — so it cannot be the authority. Use the callbacks as wake-ups and the *files* as truth: on each callback, re-check the run directory against the expected output set. Writes must land via temp-name-plus-rename or the head will read a truncated plan on a callback that arrived first.
- **Partial runs are the normal case, not the exception.** One investigator will die, wedge, or produce three thin paragraphs. The run must complete on a quorum rather than blocking on all N, and a thin contribution must be *discardable* rather than averaged in. Design the completion condition as "quorum reached or deadline exceeded", never "all N" — a callback that never arrives must not hang the run, which is why the deadline is not optional even with the callbacks in place.
- **Do not suppress standing orders on phase-1 dispatches, and make sure nothing else does.** The `standingOrders: false` payload field sits on the same verb and is the obvious-looking way to "isolate" the investigators — it is a trap. Suppressing the block removes the whole team prompt, callback included, and silently converts the run from callback-driven to deadline-only, which looks identical until an investigator finishes early and nobody notices. If a phase-1 send needs the flag for some other reason, the completion condition must be re-derived, not assumed.
- **The head role is shared global state.** A planning team claims a head role exclusively, and the delegate budgets (8 per head, 32 live) are shared with every other live team. A run started while a coding team is up can fail its pre-flight in `instantiateAgentGroupCore` — which is the good outcome, since it refuses before creating anything. Surface that refusal as "the fleet is busy", not as a generic error.

## Edge-Case & Dependency Audit

**Race Conditions** — N investigators writing concurrently into one run directory. Distinct filenames per agent make this safe, but each write must be atomic (temp file + rename) so the lead's watcher never observes a half-written plan. If the lead begins reading on the *first* file rather than on quorum, it will anchor on whichever agent finished first, which reintroduces the exact bias the run exists to remove — so the read must not start until the completion condition fires. On the dispatch side, `sendPromptToPty` serialises per terminal through `withTerminalLock` (`src/standalone/ptyPromptDelivery.ts:24`, `:41`), so an N-way fan-out to N *distinct* seats is genuinely concurrent while two sends aimed at the same seat queue rather than interleave.

**Security** — no new surface. Dispatch uses the existing authenticated verb rail; the run directory is inside the workspace.

**Side Effects** — the run directory is new state under `.switchboard/`. It must NOT be under `.switchboard/plans/`, at any nesting depth (blocker 2 above). `.switchboard/planning-runs/<run-id>/` is proposed. Note the adjacent existing name: `.switchboard/planning-cache/` is already taken by the Planning-panel document cache (`PlanningPanelCacheService.ts:48`) and is registered in `ControlPlaneMigrationService.SWITCHBOARD_RESERVED_DIRS` (`:103-104`). `planning-runs` vs `planning-cache` is close enough to misread — either pick a more distinct name or add the new directory to the reserved set deliberately. Since this directory has never existed in a released version, per the repo's migration rule it can take clean breaks with no compat shim. Consider whether run directories should be pruned or archived — N plans per run accumulates.

A second, quieter side effect: a custom `team.prompt` persists as a standing order in the DB and outlives the run. It is not scoped to a run and nothing prunes it (`agentGroupInstantiation.ts:85` notes exactly this — "nothing ever pruned orders"). Anything written there is effectively permanent for that head name until edited by hand.

**Dependencies & Conflicts** — **depends on the teams feature** (`terminals.agentGroups`, `teamWiring.ts`, `spawnDelegates`, the auto-start trigger) and extends it rather than duplicating it. Two shared-state couplings follow: the planning team claims a **head role** exclusively (a collision makes it `unassigned` and silently non-auto-starting); and its members consume the **delegate budget** shared with any live coding team (8 per head, 32 live). The standing-order budget is no longer a constraint — `MAX_ORDERS` was retired. No conflict with the plan watcher provided the run directory stays outside `.switchboard/plans/`. Adjacent to but independent of the existing planner batch dispatch at `KanbanProvider.ts:5953`, which keeps its M-plans-to-one-prompt semantics untouched. Blocks plan 02, which consumes the run directory this plan produces.

**Project-PRD interaction (Browser Switchboard).** `ptySendPrompt` sits on the **terminals** rail (`/terminals/verb/…`, `LocalApiServer.ts:3780`), which is separate from the panel verb rails the PRD's return-contract ratchet and `verbSchemas.ts` govern — `ptySendPrompt` appears in neither `verbSchemas.ts` nor `src/generated/verbAllowlist.ts` nor `protocol-catalog.json`. Reusing it therefore incurs no ratchet or schema obligation. But if this plan adds **any new panel verb** (e.g. a `planningRunStart` on the planning rail), PRD contracts #4, #5 and #7 bind: it must return its result in the body (never a bare `{success:true}`), carry a permissive field-accurate schema, appear in the allowlist/catalog so `npm run parity:check` stays green, and be wired in **both** hosts — Layer 1 without Layer 2 is "migrated-but-unreachable", Layer 2 without Layer 1 is "reachable-but-empty", and neither is done.

## Dependencies

The **teams feature** — team definitions in `terminals.agentGroups`, `spawnDelegates` / `instantiateAgentGroupCore`, `wireSpawnedTeam`, the relationship presets in `linkPresets.ts`, the team `prompt` carrier, and the auto-start trigger in both hosts' `handlePtyVerb`. This plan composes with all of it and replaces none of it.

No dependency on the other two plans — this is the first of the three.

## Adversarial Synthesis

**Risk Summary.** The three concentrated risks are all in the brief, not the plumbing: a diagnosis leaking into either brief carrier (which silently destroys the independence the run is paying N× for), a per-run brief placed in `team.prompt` where `wireSpawnedTeam`'s idempotency guard freezes it at run 1, and a custom `team.prompt` that overrides rather than merges the default and so deletes both the completion callback and the git-safety directive. Secondary risks are a truncated read of a draft on an early callback, and a run that hangs waiting for all N. Mitigations: split the brief by lifetime (invariant → team prompt, per-run/per-seat → dispatch), run the hygiene guard over both carriers, require any custom team prompt to re-include `AGENT_GROUP_CALLBACK_INSTRUCTION` + `GIT_SAFETY_DIRECTIVE` verbatim, write drafts via temp-name-plus-rename, and complete on quorum-or-deadline with the files as the authority and the callbacks only as wake-ups.

## Implementation

1. Define the run directory layout — `.switchboard/planning-runs/<run-id>/` containing `brief.md` and one `plan-<agent>.md` per investigator. Confirm nothing in the plan-watcher enumeration path (`_listSupportedLocalPlanPaths`, `TaskViewerProvider.ts:15734`) or either watcher (`:13867`, `:13940`) reaches it, and check the *configured plan folder* watcher too (`:14611` / `:14620`, recursive `**/*.md` over an operator-chosen directory) — an operator who points that at `.switchboard/` would pull the run directory in through a path the `.switchboard/plans/` reasoning does not cover.
2. **Author the brief in two parts, split by lifetime.**
   - **Invariant part → the team definition's `prompt`.** Section schema required by the repo's authoring protocol, the cite-`file:line` rule, the "write only to your own output path, never read a sibling's" rule, and — mandatorily — `AGENT_GROUP_CALLBACK_INSTRUCTION` (`teamWiring.ts:53`) and `GIT_SAFETY_DIRECTIVE` (`agentPromptBuilder.ts:558`) re-included verbatim, because supplying `prompt` replaces the default rather than extending it. Written once; do not put run-specific text here (`wireSpawnedTeam`'s `(scope, teamId)` existence check will never update it).
   - **Per-run part → `brief.md` and the dispatch body.** Symptom, scope, and the per-agent entry point. Withhold any root-cause hypothesis.
3. Define the entry-point roster (failing behavior / tests and contracts / git history / architecture) as data, not hardcoded prose, so fleet size is configurable. Note the split: the roster lives at the **dispatch** layer, not in the team definition. A team member spec with `count: 4` yields four *identical* seats and one shared team prompt; what differentiates an investigator is the per-seat dispatch tail, so the team stays a plain `{ role, count, relationship: 'reports-to-head', scope: 'per-team' }` and the entry points are assigned to seats at dispatch time by index.
4. **Provision the seats as a team, not with a new spawner.** Author a planning team definition (head role per User Review 2, one member spec with `count` = fleet size, plus the `prompt` from step 2) and let the existing auto-start trigger spawn it: creating the unparented head terminal calls `findTeamForHeadRole` and injects `delegates: team.members` and `teamName` (`bootstrap.ts:1247-1272`). This inherits the two-cap pre-flight, the team-prompt wiring, the terminals-group registration and the layout choice. Do not call `spawnDelegates` directly and do not re-implement the cap arithmetic — `instantiateAgentGroupCore` already refuses cleanly *before* creating anything, which is the behaviour that avoids orphan agent CLIs.
5. Add the fan-in dispatch — the one genuinely new mechanism: the same per-run brief to every seat, with a distinct entry point and distinct output path per seat. Reuse the existing PTY prompt delivery (`sendPromptToPty`, `src/standalone/ptyPromptDelivery.ts:36`, via the `ptySendPrompt` verb) rather than writing a second sender. Investigators are idle at dispatch time, so stdin delivery is correct — this is the dispatch case, not the mid-flight coordination case. Two payload fields matter: pass `clearBeforePrompt: true` explicitly (the omitted-field default resolves to `false` in both hosts — `bootstrap.ts:1445-1447`, `TaskViewerProvider.ts:2768-2775`; note the third state, `clearBeforePromptFromConfig: true`, which asks the host to resolve the config default and is the webview drop path's opt-in — do not use it here, a seat inheriting context from a prior task is a silent independence leak), and **leave `standingOrders` alone** so the team prompt and its callback survive.
6. Scope each seat to its own output path — the only real independence mechanism, since the teams topology already makes peer messaging inexpressible. Never hand a seat the run directory.
7. Add a brief-hygiene guard that fails the run when **either** brief carrier contains root-cause language — `brief.md` *and* the team definition's `prompt`. This is the durable half of the plan — the independence property is destroyed by prose, not by code, so the check has to live at the prose layer, and it has to cover every path prose reaches an investigator by.
8. Add run completion detection on top of the callbacks teams delivers: wake on each `reports-to-head` message, re-check the run directory against the expected output set, complete on quorum or deadline, and record which investigators contributed. Files are the authority, callbacks are only the wake-up. Writes land via temp-file-plus-rename so no partial read is possible.
9. Emit a run manifest recording run id, brief path, team id and head role, **the team prompt text actually in force**, roster, per-agent status and completion reason, so plan 02 has a typed input rather than having to infer the run's shape from directory contents — and so plan 02 can discount shared-input agreement (see Complex / Risky).
10. Decide the teardown policy explicitly. `kill(head)` cascades to per-team members (`ptyFleetService.ts:647`, `:654`), so ending the run is one call — but a run whose head is killed mid-flight loses every investigator and its callbacks. Either keep the head alive until the manifest is written, or treat a head death as a run abort with whatever files landed.

## Proposed Changes

### Run directory + manifest (new)
- **Context:** No isolated location exists for draft plans; `.switchboard/plans/` is auto-imported.
- **Logic:** `.switchboard/planning-runs/<run-id>/` holding the brief, per-agent drafts and a manifest. The manifest records the in-force team prompt alongside the roster.
- **Edge Cases:** Must stay outside every plan-watcher glob including the operator-configured one; atomic writes; unbounded growth over many runs.

### Brief author + hygiene guard (new)
- **Context:** Nothing composes a shared problem statement for a fleet, and nothing stops it carrying a diagnosis. Two carriers exist, and only one of them is a file.
- **Logic:** Emit the per-run brief from the problem statement; author the invariant half as the team `prompt`; fail the run if *either* asserts a root cause.
- **Edge Cases:** Over-eager guard rejecting a legitimate symptom description; the guard must key on causal claims, not on the presence of file paths; a guard that inspects only `brief.md` misses the team prompt entirely.

### Planning team definition (new data, no new code path)
- **Context:** Teams already provisions a head plus N members, wires the team prompt, registers the group and enforces the caps. A planning run needs a team definition, not a spawner.
- **Logic:** One team in `terminals.agentGroups` — dedicated `headRole`, one member spec `{ role, count, relationship: 'reports-to-head', scope: 'per-team' }`, and a `prompt` carrying the invariant brief plus the re-included callback and git-safety text.
- **Edge Cases:** Head-role collision leaves the team `unassigned` and silently non-starting; a `count` above 8 fails the per-head cap; `scope: 'shared'` would wrongly survive teardown and be reused across runs; a supplied `prompt` that omits the callback deletes the completion signal; the team-scoped order is never updated after first write.

### Fan-in dispatch path (new — the only new dispatch mechanism)
- **Context:** `triggerBatchAgentFromKanban` collapses M plans into one prompt for one terminal (`handleKanbanBatchTrigger`, `TaskViewerProvider.ts:6233`). `team.prompt` fans one text to N seats but cannot vary per seat and starts no turn. `ptyCreateBatch` fans seat *creation* but delivers no prompt. The per-seat, turn-starting transpose exists nowhere.
- **Logic:** Deliver the same per-run brief to every member of the planning team, varying only the entry point and the output path, over the existing `ptySendPrompt` verb.
- **Edge Cases:** Fewer live members than roster entries; an investigator dying mid-run; quorum vs all-N completion; `clearBeforePrompt` omitted (resolves `false`, leaks prior context); `standingOrders: false` passed by mistake, which deletes the team prompt and its callback.

### Architecture note — where this code lives
- **Context:** The plan does not currently say whether the run mechanism is TypeScript in the extension/standalone services or a skill under `.agents/skills/`. The answer changes the obligations materially.
- **Logic:** Decide before coding. A **skill** implementation (the head follows a documented procedure, shelling out to the existing HTTP surface) adds no verbs, no schemas, no ratchet movement, and works in both hosts by construction — the cheapest path, and the one the brief-hygiene guard's prose-layer nature already points at. A **service** implementation earns typed state and machine-checked completion but takes on PRD contracts #4/#5/#7 in full.
- **Edge Cases:** A hybrid that puts the run directory in TypeScript and the brief discipline in a skill is legitimate, but each half must be explicit about which it is; a new panel verb added without both-host wiring is incomplete by PRD contract #7 regardless of tests passing.

### Run completion on top of the team callbacks
- **Context:** Teams delivers a `reports-to-head` instruction inside the team prompt; contract #2 refuses to trust agent-authored text as a control signal.
- **Logic:** Wake on callbacks, reconcile against the files, complete on quorum or deadline.
- **Edge Cases:** A callback arriving before the file is renamed into place; a member that never calls back; the head being killed mid-run, which cascades teardown to every investigator.

## Verification Plan

1. A run with four investigators produces exactly four draft plans in `.switchboard/planning-runs/<run-id>/` and **zero** new cards on the kanban board — confirming the drafts are outside the watched tree.
2. Each draft is a complete plan against the repo's section schema, not a fragment or a partial investigation report.
3. The four drafts show substantive divergence on at least one claim when run against a problem with a known counterintuitive answer. Four near-identical drafts mean the entry points aren't producing independent trajectories and the roster needs work — this is the test that the design's core premise holds.
4. No draft references another investigator's findings or output path — the independence property, checked by inspection of all four.
5. Every investigator's prompt **does** carry a `=== STANDING ORDERS ===` block containing the `reports-to-head` instruction — verified in the delivered text, not at the call site. Its absence means a `standingOrders: false` crept onto the dispatch, **or** a custom `team.prompt` overrode the default without re-including the callback; either way the run has silently lost its completion callbacks.
6. A planning team whose `prompt` omits the callback text is rejected at authoring time (or the run refuses to start) rather than starting a run with no completion signal.
7. A **second** run on the same planning team delivers the *second* run's brief, not the first's — the `wireSpawnedTeam` idempotency trap. Verified by running twice with different symptoms and diffing the delivered prompts.
8. Starting the planning team's head spawns exactly `count` investigators via auto-start, with no bespoke spawn call in the run code path — verified by the `[bootstrap] Team auto-start:` log line naming the team and member count.
9. A planning team whose head role collides with an existing team is reported to the operator as unassigned rather than silently failing to start — the failure mode `migrateAgentGroups` step 3 creates.
10. A run requested while the delegate budget is exhausted is refused by `instantiateAgentGroupCore`'s pre-flight with no terminals created — no orphan head left behind.
11. Neither brief carrier contains a root-cause assertion, and the hygiene guard fails on a diagnosis injected into `brief.md` **and, separately,** on one injected into the team `prompt`.
12. Killing one investigator mid-run still completes the run on quorum, with the manifest recording which agent did not contribute.
13. A draft observed by the lead is never truncated — verified by reading the run directory under concurrent investigator writes, and specifically by forcing a callback to arrive before its file is renamed into place.
14. The run manifest records the team prompt text actually in force, so plan 02 can identify shared inputs.
15. Existing team behaviour is unregressed: a normal coding team still auto-starts, wires its team prompt and tears down on head kill with this feature present.
16. `npx tsc --noEmit` introduces no new errors against the pre-existing baseline (re-verified 2026-08-16: exactly 5 errors, all `TS2835` extensionless-relative-import complaints in `ClickUpSyncService.ts:3165`, `KanbanProvider.ts:9263`, `NotionFetchService.ts:704` and `TaskViewerProvider.ts:11242` / `:11296` — unrelated to this work).

### Automated Tests

- Unit: the brief-hygiene guard rejects causal language in `brief.md` and in a team `prompt`, and accepts a symptom description containing `file:line` references (the false-positive case).
- Unit: the per-seat dispatch builder emits N payloads with identical brief bodies, distinct entry points, distinct output paths, `clearBeforePrompt: true`, and no `standingOrders` key.
