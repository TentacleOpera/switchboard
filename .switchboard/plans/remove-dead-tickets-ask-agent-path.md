# Remove the dead tickets ask-agent path

## Goal

Delete the `ticketsAskAgent` verb and its webview helper. The button it served was removed when ticket collaboration moved to downloading tickets as local `.md` files, so the whole path is unreachable — but its comment tells the next reader it is being kept on purpose, which makes it worse than ordinary dead code.

### Problem Analysis

`handleTicketsAskAgent` in `src/webview/tickets.js` carries this comment:

> "Ask-agent posts the ticket to a coding agent via the host. Currently not bound to a button (the Agent API modal copies prompts instead), but the verb handler now lives on TicketsPanelProvider so this helper is preserved for future wiring. Verbatim from planning.js."

The comment is wrong about intent. The wiring was not left pending — it was **deliberately removed** when the design changed: ticket collaboration now happens by pressing prominent link buttons that hand an agent a path to the downloaded `.switchboard/tickets/<provider>/*.md` file. Ask-agent is not a feature awaiting a button; it is a superseded approach.

That makes it a trap rather than clutter. "Preserved for future wiring" instructs anyone reading it — human or agent — to leave it alone and, worse, invites someone to "finish" it. It also inflates the tickets verb surface, and every verb in `TICKETS_VERBS` is a live entry point that payload validation and the return-contract ratchet must account for.

The surviving surface:

| Location | What |
| :--- | :--- |
| `src/webview/tickets.js:4787` | `handleTicketsAskAgent` posts `{ type: 'ticketsAskAgent' }` — called by nothing |
| `src/webview/tickets.js:8274` | `case 'ticketsAskAgentResult'` response arm |
| `src/services/TicketsPanelProvider.ts:4048` | `case 'ticketsAskAgent'` handler |
| `src/services/TicketsPanelProvider.ts:4055`, `:4074`, `:4078` | three `ticketsAskAgentResult` posts |
| `src/generated/verbAllowlist.ts:11` | `ticketsAskAgent` in `TICKETS_VERBS` |
| `src/webview/planning.js:5218`, `src/services/PlanningPanelProvider.ts:5123` | comments recording the 2f move out of planning |

### Root Cause

The 2f refactor moved ask-agent from planning into tickets while its button was being removed. The move was mechanical and faithful; nobody revisited whether the destination should exist. The "preserved for future wiring" note was a reasonable guess at the time and has since been contradicted by the product decision, but nothing prompted a re-read.

### Non-goals

- Changing the Agent API modal or the ticket link buttons. Both are the intended paths and stay exactly as they are.
- Touching `get-tickets` or any other protocol. `get-tickets` remains the sanctioned fallback for metadata that was never downloaded.
- Regenerating `verbAllowlist.ts` by hand — it is build-generated.

## Complexity Audit

### Routine

- Deleting `handleTicketsAskAgent` and its comment from `src/webview/tickets.js`.
- Deleting the `ticketsAskAgentResult` case from the webview message switch.
- Deleting the `ticketsAskAgent` case and its three result posts from `TicketsPanelProvider`.
- Updating the two 2f-history comments so they stop naming a verb that no longer exists.

### Complex / Risky

- **`verbAllowlist.ts` is generated, not hand-edited** (`src/generated/`, "Do not hand-edit; regenerated by the verb-engine tooling"). Removing the verb means regenerating it, and the regeneration must not churn unrelated entries — the diff should be one removed string.
- **The return-contract ratchet.** `scripts/check-verb-return-contract.js` gates verb arms. Removing an arm must not trip it, and the ratchet's own count (if it holds one) may need updating in the same commit.
- **Both hosts route tickets verbs.** The extension host and the browser host each wire a tickets verb router; the verb must disappear from both, or the browser host keeps an arm the allowlist no longer permits.
- **Confirm it is genuinely unreachable before deleting.** The only caller is `handleTicketsAskAgent`, which nothing calls — but `TICKETS_VERBS` is also the allowlist for `/tickets/verb/*` over HTTP, so the verb is reachable by an external caller (an agent script, a curl) even with no UI. That is an argument for removal, not against, but it means "no UI caller" is not the same as "no caller"; check `.agents/` and `scripts/` for any use before deleting.

## Edge-Case & Dependency Audit

**Race conditions**
- None. Removing an unreachable arm.

**Security**
- Mildly positive: one fewer verb on the loopback HTTP surface. `ticketsAskAgent` accepts a provider and ticket id and dispatches to a terminal, so it is a prompt-injection surface reachable by anything that can reach the port. Removing it is a small reduction.

**Side effects**
- Tests referencing the verb will fail and should be deleted with it, not skipped. Check `src/test/*ticket*` and the connections-routing contract test.
- If `verbAllowlist.ts` regeneration produces unrelated changes, that is a signal the generator has drifted from source — worth noting rather than committing blind.

**Migration**
- None. No user data, no persisted state, no settings key. This is unreleased-behaviour cleanup in the sense that matters: nothing a user can currently do stops working, because nothing currently invokes it.

## Dependencies

- Independent of everything else. Suitable for the backlog.

## Adversarial Synthesis

**"It is only a few lines — leave it."** The lines are cheap; the comment is not. It asserts an intent the product has abandoned, and it is exactly the kind of note that gets a superseded approach revived by someone trying to be helpful. Deleting the code without deleting the claim would be the worse half of the job.

**"Keep it in case ask-agent comes back."** If it does, it comes back against the current design — tickets as local `.md` files — not as a 2018-era post-to-terminal handoff. Git has the old shape.

**"It is reachable over HTTP, so it is not dead."** True and the reason it is worth removing rather than merely ignoring: an unreachable-from-UI verb that still accepts input over loopback is a surface nobody is maintaining.
