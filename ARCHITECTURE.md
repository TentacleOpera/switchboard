# Architecture — Navigational Map

> **What this is.** A map of *where things live* in the Switchboard codebase, organised by
> panel and by folder. It is the entry point for an agent (or human) orienting before a
> task: read this first, then go to the specific file.
>
> **What this is NOT.** It is not a rules document (see `CONSTITUTION.md` for invariants) and
> not a deep runtime audit (see `docs/TECHNICAL_DOC.md` for how things work internally). This
> file is regenerable by an agent in a few minutes — line references are approximate and will
> drift; the *structure* (which file serves which panel) is stable.
>
> **Last regenerated:** Aug 2026.

## Folder layout

| Path | Role |
| :--- | :--- |
| `src/` | **Source of truth.** All TypeScript/JavaScript source. Never read `dist/` (see README "For AI agents"). |
| `src/webview/` | Frontend views — one HTML + one client JS per panel, plus shared CSS/utils. Sandboxed iframes that talk to the host only via `postMessage` (editor host) or `window.parent.postMessage` + HTTP verbs (browser host). |
| `src/services/` | Backend providers and sync services. One `*PanelProvider.ts` per panel handles `postMessage` arms and exposes verb arms; plus standalone services (KanbanDatabase, LocalApiServer, sync services, etc.). |
| `src/standalone/` | The browser/`npx` host. `bootstrap.ts` constructs the same services and wires the same verb routers into `LocalApiServer` as the extension host. `ptyBackend.ts`/`ptyHost.ts`/`terminalWsGateway.ts` implement the `node-pty` terminal backend. |
| `src/generated/` | Build-generated allowlists — `verbAllowlist.ts` is the per-provider catalogue of verbs the generic dispatcher accepts. Do not hand-edit; regenerated by the verb-engine tooling. |
| `src/utils/` | Small shared utilities (loopback hostname, panel revival, notifications, location guard). |
| `src/lifecycle/` | Workspace cleanup lifecycle hooks. |
| `src/models/` | Shared type/model definitions (LiveSync, Pipeline). |
| `src/test/` | Test suite — ~220 files, regression-heavy. Naming convention `*-regression.test.js`/`.ts`. |
| `dist/` | **Webpack build artifact.** Produced by `npm run compile`; NOT used in development or testing (testing uses an installed VSIX). Do not search or read it. |
| `docs/` | Reference docs (`TECHNICAL_DOC.md`, `IPC_PROTOCOL.md`, `VERB_ENGINE_RECIPE.md`, `SECURITY-AUDIT.md`, etc.). |
| `.agents/` | Workflow contracts and skills — `workflows/` (slash-command protocols), `skills/` (invokable capabilities). |
| `.switchboard/` | Runtime data — `plans/`, `features/`, `kanban.db`, workspace state. Written by the running extension/standalone host. |
| `scripts/` | Build/check scripts — `check-verb-return-contract.js` (the return-contract ratchet), `analyze-verb-migration2.js`, kanban move-card helpers, etc. |
| `design_system/`, `designs/` | Design-system starter templates and per-workspace design assets. |

## Feature-to-file mapping

One row per UI panel. "Backend provider" is the `*PanelProvider.ts` that owns the panel's
`_handleMessage` switch and verb arms. The Connections panel is a thin forwarder — it owns no
verb arms, it routes to Setup/Planning providers (see its header comment).

| Panel | HTML | Client JS | Backend provider | Key test files |
| :--- | :--- | :--- | :--- | :--- |
| Kanban (Board) | `src/webview/kanban.html` | (inline in HTML) | `src/services/KanbanProvider.ts` | `src/test/*kanban*`, `src/test/*board*`, `src/test/*column*` |
| Planning | `src/webview/planning.html` | `src/webview/planning.js` | `src/services/PlanningPanelProvider.ts` | `src/test/*planning*`, `src/test/*brain*`, `src/test/*plan-*` |
| Design | `src/webview/design.html` | `src/webview/design.js` | `src/services/DesignPanelProvider.ts` | `src/test/*design*` |
| Setup | `src/webview/setup.html` | (inline in HTML) | `src/services/SetupPanelProvider.ts` | `src/test/*setup*`, `src/test/*control-plane*` |
| Project | `src/webview/project.html` | `src/webview/project.js` | `src/services/PlanningPanelProvider.ts` (project tab routes through the planning provider) + `src/services/TaskViewerProvider.ts` | `src/test/*project*`, `src/test/*constitution*` |
| Tickets | `src/webview/tickets.html` | `src/webview/tickets.js` | `src/services/TicketsPanelProvider.ts` | `src/test/*ticket*`, `src/test/*linear*`, `src/test/*clickup*` |
| Connections (Remote Control / Web Agents) | `src/webview/connections.html` | `src/webview/connections.js` | `src/services/ConnectionsPanelProvider.ts` (forwarder → Setup/Planning) | `src/test/connections-routing-contract.test.js` |
| Terminals | `src/webview/terminals.html` | `src/webview/terminals.js` | `src/services/TaskViewerProvider.ts` (terminal fleet) + `src/standalone/pty*.ts` (browser host) | `src/test/*terminal*`, `src/test/browser-*terminal*` |
| Memo | `src/webview/memo.html` | `src/webview/memo.js` | `src/services/TaskViewerProvider.ts` (memo arms) | `src/test/*memo*` |
| Shell / activity bar | `src/webview/shell.html` | `src/webview/shell.js` | — (browser-host shell only) | — |

Shared webview assets: `src/webview/sharedUtils.js`, `src/webview/sharedDefaults.js`,
`src/webview/shared-tabs.css`, `src/webview/markdownEditor.js`, `src/webview/transport.js`
(browser-host WebSocket transport — separate protocol layer, not in `IPC_PROTOCOL.md`).

Panel HTML is produced by one shared module — `src/services/headlessPanelHtml.ts` — so neither
host forks the UI. Adding a panel means: a getter there, a route in `LocalApiServer`, a
`/panels` manifest row, and (for verbs) a verb router in **both** hosts.

## Major services in `src/services/`

| Service | One-line role |
| :--- | :--- |
| `KanbanProvider.ts` | Board panel host — card moves, dispatch prompts, orchestration, autoban, worktrees, features. Largest provider (~14.5k lines). |
| `TaskViewerProvider.ts` | Terminal-fleet + memo + onboarding host; routes setup/tickets/linear/clickup verbs. Largest file (~26.5k lines). |
| `PlanningPanelProvider.ts` | Planning + Project panel host — docs, plans, constitution, PRD, insights, online sync. (~7.4k lines) |
| `DesignPanelProvider.ts` | Design panel host — design systems, Stitch integration, HTML/Claude folders. |
| `SetupPanelProvider.ts` | Setup panel host — settings, control-plane, DB path, workspace mappings, remote config. |
| `TicketsPanelProvider.ts` | Tickets panel host — ClickUp/Linear ticket CRUD, sync, comments, attachments. |
| `ConnectionsPanelProvider.ts` | Thin forwarder — routes Connections-panel verbs to Setup/Planning providers. Owns no arms. |
| `KanbanDatabase.ts` | `sql.js` database layer — `kanban.db`, plans, worktrees, features, config table. (~10.7k lines) |
| `LocalApiServer.ts` | The localhost HTTP server exposing verbs (`/kanban/verb/*`, `/terminals/verb/*`), `/panels` manifest, kanban moves, terminal relay. The browser-host surface. |
| `ClickUpSyncService.ts` / `LinearSyncService.ts` | Two-way ticket sync with ClickUp / Linear. |
| `ContinuousSyncService.ts` | Debounced continuous (live) sync loop. |
| `NotionBackupService.ts` / `NotionFetchService.ts` / `NotionBrowseService.ts` | Notion backup/restore and browse. |
| `RemoteControlService.ts` | Remote Control (Linear/Notion-driven card) bridge. |
| `ArchiveManager.ts` / `AutoArchiveService.ts` | DuckDB archive of historical plans/conversations. |
| `hostSeams.ts` | The host-agnosticism seams — config/paths/secrets/UI/clipboard/terminal interfaces providers reach the host through (never `vscode.*` directly in arms). |
| `verbSchemas.ts` | Per-verb payload validation at the HTTP boundary. Shared across all provider work. |
| `broadcastHub.ts` | Cross-panel/cross-client broadcast fan-out. |
| `headlessPanelHtml.ts` | Shared panel-HTML producer for both hosts. |
| `agentPromptBuilder.ts` | Composes dispatch prompts (per-role, per-complexity, feature/plan). |
| `agentConfig.ts` | Agent/role/column config parsing. |
